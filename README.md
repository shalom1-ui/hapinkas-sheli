# הפנקס שלי — שרת Backend

שרת אמיתי, פועל, לניהול תקציב אישי, חונכות, מעגל מטפלים, ומנוע שיחה קולית (IVR) בעברית חופשית — ללא לחיצת מקשים וללא SMS בשום מקום.

## למה אפס תלויות חיצוניות (0 packages)?

השרת נכתב כך שהוא רץ אך ורק עם היכולות המובנות של Node.js (גרסה 22 ומעלה) — ללא Express, ללא ספריות בסיס נתונים, ללא ספריות הצפנה חיצוניות. זה נבחר כדי שהקוד ירוץ בכל סביבה בלי תלות בזמינות רשת להתקנת חבילות, ובלי סיכוני אבטחה של תלויות צד-שלישי. בפועל:

| צורך | מה השתמשנו בו |
|---|---|
| שרת HTTP + ניתוב | `node:http` + נתב פשוט שכתבנו (`src/router.js`) |
| מסד נתונים | `node:sqlite` המובנה של Node (קובץ יחיד, בלי שרת נפרד) |
| הצפנת סיסמאות | `crypto.scryptSync` (שקול אבטחתית ל-bcrypt) |
| טוקן התחברות | JWT מינימלי שכתבנו לבד עם `crypto.createHmac` |
| קריאות לשירותים חיצוניים (Twilio, Cardcom) | `fetch` המובנה |

אפשר להוסיף בעתיד Express/PostgreSQL וכו' אם ירצו להרחיב, אך זה לא הכרחי — השרת כפי שהוא מוכן לעבודה אמיתית.

## הצגה מרחוק (למשל לחבר, בלי שהוא צריך להתקין משהו)

### הדרך הקלה - קובץ הפעלה אחד

בתיקיית `backend` יש קובץ בשם **`הפעלה-עם-לינק-לחבר.bat`**. לחיצה כפולה עליו פותחת אוטומטית שני חלונות - אחד עם השרת ואחד עם קישור השיתוף - בלי צורך להקליד פקודות בעצמכם. בחלון השני (שנקרא "קישור לחבר") תופיע שורה `your url is: https://...` - זו הכתובת ששולחים לחבר.

**חשוב:** שני החלונות שנפתחים חייבים להישאר פתוחים כל עוד רוצים שהקישור יעבוד. אם המחשב נכנס למצב שינה, או שסוגרים אחד מהחלונות בטעות, הקישור מפסיק לעבוד - פשוט הריצו את הקובץ שוב.

יש גם קובץ `הפעלה-מקומית.bat` שמפעיל רק את השרת (בלי קישור לחבר) - לשימוש רגיל במחשב עצמו.

### הדרך הידנית (אותו דבר, שלב-שלב)

השרת רץ רק על המחשב שלכם (`localhost`), אז כברירת מחדל אף אחד מבחוץ לא יכול להגיע אליו. כדי לשתף אותו זמנית עם מישהו אחר - בלי לפרוס שום דבר לענן - אפשר להשתמש ב"מנהרה" (tunnel) שיוצרת כתובת אינטרנט זמנית שמצביעה על המחשב שלכם:

1. משאירים את החלון שבו `node src/server.js` רץ **פתוח** (אל תסגרו אותו).
2. פותחים חלון PowerShell **נוסף** (חדש), נכנסים לתיקיית `backend`, ומריצים (ב-Windows, אם `npx` רגיל חסום ע"י מדיניות הרצת סקריפטים, יש להשתמש ב-`npx.cmd`):
   ```
   npx.cmd localtunnel --port 3000
   ```
   (בפעם הראשונה זה יוריד חבילה קטנה - זה תקין, אין צורך בהרשמה לשום שירות.)
3. תוך כמה שניות תופיע שורה עם כתובת כמו `your url is: https://short-name-12.loca.lt` - זו הכתובת ששולחים לחבר.
4. כשהחבר נכנס לכתובת הזו בפעם הראשונה, ייתכן שיראה מסך ביניים של השירות שמבקש ללחוץ "Click to Continue" (חד פעמי) - זה תקין ולא קשור לאפליקציה שלכם.

   בנוסף, כל מי שנכנס ללינק (גם אתם וגם החבר) עשוי להתבקש להזין "סיסמת מנהרה" - זה בדיוק כתובת ה-IP הציבורית של המחשב שממנו הוא נכנס. כל אחד מקבל אותה בעצמו על ידי כניסה מהמחשב שלו לכתובת https://loca.lt/mytunnelpassword (אי אפשר להעביר סיסמה אחת לכולם - לכל אחד יש ערך שונה, לפי הרשת שלו).
5. כשסוגרים את חלון ה-PowerShell של `localtunnel`, הכתובת מפסיקה לעבוד. הרצה חדשה של הפקודה נותנת כתובת אקראית חדשה בכל פעם.

### כתובת קבועה שלא משתנה בכל הרצה (מומלץ, כדי לא לשלוח לינק חדש כל פעם)

localtunnel מאפשר לבחור שם קבוע לכתובת בעצמכם, במקום שם אקראי, על ידי הוספת `--subdomain`:
```
npx.cmd localtunnel --port 3000 --subdomain hapinkas-sheli
```
זה ייתן כתובת קבועה: `https://hapinkas-sheli.loca.lt`. חשוב לדעת:
- זו לא הרשמה/הזמנה של השם - זה רק ניסיון לתפוס אותו בכל הרצה. אם מישהו אחר בעולם תופס בדיוק את אותו שם באותו רגע, תקבלו הודעת שגיאה ותצטרכו לבחור שם אחר (אפשר לשנות ל-`hapinkas-sheli-2` וכו').
- השם נשמר רק כל עוד המנהרה פתוחה - ברגע שסוגרים את החלון, השם משתחרר, וכל אחד (כולל אתם) יכול לתפוס אותו מחדש בפעם הבאה כרגיל.
- אם השם תפוס אצל מישהו אחר, זה בדרך כלל זמני - נסו שוב כעבור כמה דקות, או בחרו שם ייחודי יותר.

חשוב: כל עוד המנהרה פתוחה, מי שיש לו את הכתובת יכול לגשת למה שרואים ב-`http://localhost:3000` - כלומר לאותו מידע בדיוק שיש במסד הנתונים המקומי שלכם (כרגע מידע בדיקה בלבד). זה מתאים להדגמה מהירה וזמנית, לא כפתרון קבוע - למעבר אמיתי לייצור עם כתובת קבועה ראו את סעיף "מדריך פריסה לייצור" למטה.

## מנוע השיחה הקולית — החלטה טכנית חשובה

בתכנון המקורי דיברנו על Twilio + Google Speech-to-Text בנפרד. בפועל, בזמן הבנייה גיליתי שהתג `<Gather input="speech" language="he-IL">` של Twilio עצמו מבצע זיהוי דיבור ומחזיר את התמלול ישירות ב-Webhook הבא — בלי צורך בהזרמת אודיו נפרדת ל-Google Cloud (מה שהיה דורש תשתית WebSocket מורכבת). לכן המנוע כאן משתמש רק ב-Twilio לזיהוי הדיבור. **המשמעות המעשית: יש רק ספק אחד לשלם ולהגדיר (Twilio), לא שניים.** זה מפשט את ההקמה ומוזיל את העלות החודשית לעומת מה שדיברנו עליו בהתחלה.

מכונת המצבים המלאה (הכנסה/הוצאה/יתרה/חונכות/דיווח מטפל/הערת מפקח) נמצאת ב-`src/routes/ivr.js`, עם קריאה חוזרת (read-back) ואישור "כן" לפני כל שמירה — בדיוק כמו באב-הטיפוס.

## חיבור קו "ימות המשיח" (טלפון "כשר" עם זיהוי דיבור)

בנוסף ל-Twilio, יש תמיכה בקו IVR2 של ימות המשיח (call2all.co.il) - מיועד למי שרוצה מספר "כשר" שעובר דרך רשתות סינון. זו **אינטגרציה עצמאית**, לא תלות ב-Twilio ולא ב-npm package חיצוני (`yemot-router2` וכדומה) - מימוש-יד לאותו פרוטוקול, כדי לשמור על עקרון "בלי ספריות חיצוניות" של הפרויקט. שתי האינטגרציות (`ivr.js` ל-Twilio, `yemot.js` לימות) חולקות **בדיוק** את אותה מכונת מצבים (`advance()` המיוצאת מ-`ivr.js`) - השינוי היחיד הוא שכבת התרגום לפרוטוקול.

### הגדרה בצד ימות המשיח

1. נכנסים לניהול המערכת בימות (`https://y-www.call2all.co.il` או מהקישור שקיבלתם באימייל ההרשמה) → **מערכת תוכן** → בוחרים שלוחה (למשל שלוחה 1) → **הגדרות מתקדמות**.
2. מחליפים את תוכן ה-`ext.ini` ל:
   ```
   type=api
   api_url=https://הכתובת-שלכם.onrender.com/api/ivr/yemot
   api_url_post=yes
   ```
   (מחליפים את הכתובת בכתובת השרת האמיתית שלכם - למשל `https://hapinkas-sheli-ze65.onrender.com/api/ivr/yemot`.)
3. שומרים, ומתקשרים למספר המערכת לבדיקה.

### חשוב לדעת

- זיהוי המתקשר הוא לפי מספר טלפון (Caller ID), בדיוק כמו ב-Twilio - המשתמש חייב להיות רשום במערכת עם מספר הטלפון שממנו הוא מתקשר.
- ימות שולח את מספר המתקשר בפורמט מקומי (`0501234567`) בעוד ש-Twilio שולח פורמט בינלאומי (`+972501234567`) - השרת מזהה אוטומטית את שתי הצורות (`findUserByPhone` ב-`src/routes/yemot.js`), כך שאותו משתמש רשום מזוהה משני הספקים בלי הגדרה נוספת.
- הקלט מהמתקשר מתקבל ע"י זיהוי דיבור (`stt`), לא לחיצת מקשים - בדיוק כמו החוויה ב-Twilio.
- אם השיחה לא מזוהה, המערכת עונה בקול ומנתקת בצורה מסודרת (לא "תקלה" סתומה).

## חונכות — דיווח מעקב חופשי על מפגש

בנוסף למשך המפגש (שנקבע אוטומטית ב-checkin/checkout, או ידנית ב-quick-session), החונך יכול עכשיו לצרף `note` אופציונלי - דיווח מעקב חופשי (למשל "עבדנו על חיבור וחיסור, התקדמות יפה") - שנשמר יחד עם המפגש (`sessions.note`), מופיע בתיק המאוחד (`/file`), **וגם** מוצג להורה בסיכום (`/summary`), בדיוק כמו דוחות המטפלים. גם כאן פועל אותו "מילון" ניסוחים אישי (`kind=session_note`) להשלמה אוטומטית לתלמידים הבאים.

## חונכות — טופס "הכנה לשיעור" (דיגיטציה של טופס נייר)

`POST /api/students/:id/lesson-reports` הוא דיגיטציה של טופס נייר שהועבר בתהליך הבנייה, בנוסף למפגש הרגיל. כל השדות אופציוניים ובניסוח חופשי - הטבלה `lesson_reports` (`src/db.js`) והראוט `src/routes/lessonReports.js` שומרים בדיוק את מבנה הכותרות מהטופס המקורי: תאריך (אפשר גם עברי, כמו "יג כסלו"), שם/טלפון/שעות נוחות של המלמד, ימי לימוד, תאריך הדרכה + המלצה/תאריך להערכה חוזרת, מס' שבוע/פגישה/זמן לימוד, הקטע הנלמד בשיעור, מטרה, צורת עבודה, יישום בפועל, התחברות ושיתוף פעולה, התמודדות והשגת המטרות, הערות מהסביבה, איחורים וחיסורים.

בלוח הבדיקה, שדות שם/טלפון המלמד מתמלאים אוטומטית מהפרופיל של המשתמש המחובר (נוח, לא "שם קשיח") - ואפשר לערוך אותם. לכל שדה חופשי פועל אותו "מילון" ניסוחים אישי שכבר קיים במערכת (`kind=lesson_<שם השדה>`, למשל `lesson_topic_studied`) - הטופס מוצע להשלמה אוטומטית לתלמידים הבאים, בלי לשכפל ניסוחים מהתלמיד/הטופס הספציפי. הטופס מופיע בתיק המאוחד (`/file`) **וגם** בסיכום שההורה רואה (`/summary`) - מלבד טלפון/שעות נוחות של המלמד, שאינם רלוונטיים להורה.

## מסמכים - העלאת קבצים לתיק תלמיד

`POST /api/students/:id/documents` מאפשר להעלות קובץ (למשל את הטופס הסרוק/המקורי, או כל מסמך אחר) לתיק תלמיד. הראוט שלנו (`router.js`) תומך רק בגוף JSON (אין תלות ב-multipart/form-data חיצוני), אז ההעלאה מתבצעת כ-base64: הדפדפן קורא את הקובץ עם `FileReader.readAsDataURL` ושולח `{ title, filename, mime_type, data_base64 }`. הקובץ עצמו נשמר בדיסק (`backend/data/uploads/<student_id>/...`, ניתן לשינוי מיקום דרך `UPLOADS_DIR`), וב-DB (`documents`) נשמרת רק המטא-דאטה. **ברשימה (`GET /api/students/:id/documents`) מוצגות רק כותרות** - לצפייה בתוכן המלא יש נתיב הורדה נפרד (`GET /api/documents/:id/download`). הגבלת גודל: 15MB לקובץ. הרשאה כמו `/file` - בעלים/חונך/מטפל/מפקח בלבד, **לא** הורים (נחשב תוכן פנימי/מנהלתי).

## הורים — סיכומים בלבד, לא הצ'אט הפנימי

נוסף מודל הרשאות ייעודי להורים:

- **תפקידים מקצועיים** (`mentor`/`therapist`/`supervisor`) נקבעים בהרשמה או בעדכון פרופיל (`roles`), ורק למי שיש לו אחד מהם (או שהוא הבעלים של התלמיד) יש גישה ל-`/file` המלא ולצ'אט הפנימי (`/comments`).
- **שיוך הורה לתלמיד** נעשה מבנית דרך טבלת `student_guardians` (לא דרך "הצהרה" חופשית על תפקיד) — רק הבעלים/החונך של התלמיד יכול לשייך הורה, דרך `POST /api/students/:id/guardians` עם שם המשתמש של ההורה (שצריך להיות רשום מראש במערכת).
- ההורה רואה רק את `GET /api/students/:id/summary`: מספר מפגשים, סה"כ דקות, ורשימת הדוחות המקצועיים המלאים (זה בדיוק ה"סיכום" שההורה צריך). **אין** גישה לצ'אט הפנימי בין הצוות המקצועי, וגם **אין** גישה להערות (`student_comments`) — נתיב ה-`/summary` פשוט לא כולל אותן בכלל בתשובה.
- **סוגי דיווח מוצעים** (`role_type`): ריפוי בעיסוק, טיפול רגשי, תרפיה במוסיקה, תרפיה באומנות, תרפיה בחיות, אחר. בדיוק כמו trend, גם `role_type` יכול להיות כל ניסוח חופשי אחר (כשבוחרים "אחר" ומקלידים, למשל "פיזיותרפיה") - הרשימה היא הצעה נוחה, לא רשימה סגורה.
- **שמירה ושליחה הן שתי פעולות נפרדות**: `POST /api/students/:id/reports` תמיד שומר את הדוח בתיק המאוחד. האם לשלוח מייל להורים *עכשיו* נשלט ע"י שדה `notify_guardians` (בוליאני) בבקשה:
  - אם `notify_guardians` נשלח במפורש (`true`/`false`) — זה מה שקובע, בלי קשר למגמה (כך אפשר גם לשמור בלי לשלוח דוח עם מגמת "משתפרת", וגם לשלוח ביודעין דוח עם מגמה "יציבה").
  - אם `notify_guardians` לא נשלח בכלל — ברירת המחדל היא ההתנהגות המקורית: שולח מייל אוטומטית רק כשהמגמה היא **"משתפרת"**.
  - כדי לשלוח מאוחר יותר עדכון על דוח שכבר נשמר בלי שליחה מיידית, יש את `POST /api/reports/:id/notify` (מותר לאיש המקצוע שכתב את הדוח, או לכל בעלים/איש מקצוע אחר על אותו תלמיד).
  - בלוח הבדיקה (`test-dashboard.html`) זה מופיע כתיבת בחירה ("לשלוח עדכון במייל להורים המשויכים מיד עם השמירה") ורשימת "הדוחות שלי" עם כפתור "שלח עדכון להורים עכשיו" לכל דוח.
  - השליחה בפועל (`src/services/email.js`) פועלת במצב MOCK כרגע - ר' `.env.example`.
- **מגמה (`trend`) בניסוח חופשי**: מעבר לשלוש האפשרויות הקבועות (משתפרת/יציבה/דורשת תשומת לב), אפשר לשלוח כל טקסט חופשי (בלוח הבדיקה: לבחור "אחר" ולהקליד). רק הערך המדויק "משתפרת" מפעיל את ברירת המחדל של שליחת מייל אוטומטית - ניסוח חופשי דורש `notify_guardians: true` מפורש כדי לשלוח.
- **"מילון" ניסוחים אישי לכל איש מקצוע** (`phrase_dictionary`, `GET /api/reports/dictionary?kind=note|trend|role_type`): כל תוכן דיווח, וכל ניסוח מגמה/סוג-דיווח חופשי (לא אחת מהקטגוריות הקבועות), נשמר אוטומטית ב"מילון" האישי של איש המקצוע שכתב אותו, ומוצע כהשלמה אוטומטית (autocomplete) בפעם הבאה - גם עבור תלמידים אחרים - כדי לא להקליד את אותם ניסוחים מחדש בכל פעם.

## אבטחה ופרטיות — מה כבר מיושם

- סיסמאות מאוחסנות מוצפנות (scrypt+salt), לעולם לא בטקסט גלוי.
- התחברות דרך טוקן JWT חתום, עם תפוגה.
- שחזור סיסמה **אך ורק** בשיחה קולית אוטומטית שמקריאה קוד, או במייל — לעולם לא SMS.
- פרטי כרטיס אשראי **לעולם לא** מגיעים לשרת שלנו — הסליקה מתבצעת בדף/iframe מאובטח של Cardcom עצמם (תואם PCI-DSS).
- זיהוי מתקשר לפי מספר טלפון (Caller ID) מול הטלפון הרשום במערכת בלבד.

## מדריך פריסה לייצור — לאן לשלם ומה להגדיר

השלב הזה הוא שלכם (החלק העסקי/עמותה כבר בטיפולכם) — כאן רק ההוראות הטכניות המדויקות.

### 1. Twilio — מספר טלפון + שיחות קוליות

1. הרשמו בכתובת twilio.com וממלאים פרטי חיוב (כרטיס אשראי).
2. רוכשים מספר טלפון (מומלץ למצוא מספר ישראלי אם זמין, או מספר בינלאומי עם הפניה).
3. מהלוח הראשי (Console) מעתיקים את **Account SID** ואת **Auth Token**.
4. בהגדרות המספר שנרכש, תחת "Voice & Fax" → "A call comes in", בוחרים **Webhook**, ומדביקים: `https://הכתובת-שלכם.com/api/ivr/voice` (שיטה: HTTP POST).
5. ב-`.env` של השרת (העתיקו מ-`.env.example`) ממלאים:
   ```
   TWILIO_MOCK=false
   TWILIO_ACCOUNT_SID=...
   TWILIO_AUTH_TOKEN=...
   TWILIO_FROM_NUMBER=+972...   (המספר שרכשתם)
   PUBLIC_BASE_URL=https://הכתובת-שלכם.com
   RECOVERY_MOCK=false
   ```

חשוב: המשתמשים חייבים להיות רשומים במערכת עם מספר הטלפון שלהם בפורמט בינלאומי מלא (למשל `+972501234567`), אחרת זיהוי המתקשר לא יעבוד.

### 2. אחסון (Hosting) — היכן השרת רץ בפועל

השרת צריך שרת שרץ 24/7 עם כתובת ציבורית וכתובת HTTPS (חובה עבור Twilio), ועם **דיסק קבוע (persistent disk)** לשמירת קובץ מסד הנתונים (`data/app.db`) — אחרת המידע יימחק בכל עדכון.

אפשרויות פשוטות (לא דורשות ידע DevOps מעמיק):
- **Render.com** — "Web Service" מחובר ל-Git שלכם, עם "Persistent Disk" מחובר לתיקיית `data/`. פקודת הרצה: `npm start`.
- **Railway.app** — דומה, גם עם דיסק קבוע (Volume).
- שרת וירטואלי (VPS) כמו DigitalOcean/Linode — יותר שליטה, דורש קצת יותר הגדרה ידנית (Node.js + PM2 להרצה קבועה).

בכל אחת מהאפשרויות: מגדירים את משתני הסביבה מתוך `.env.example` בפאנל הניהול של השירות (לא מעלים את קובץ ה-`.env` עצמו ל-Git).

### 3. דומיין (אופציונלי אך מומלץ)

רוכשים דומיין (למשל דרך Namecheap/GoDaddy/ספק ישראלי), ומצביעים אותו לכתובת שקיבלתם משירות האחסון (לרוב באמצעות רשומת CNAME). מעדכנים את `PUBLIC_BASE_URL` ואת ה-Webhook ב-Twilio לכתובת הסופית.

### 4. Cardcom — הפעלת הסליקה האמיתית

מכיוון שכבר יש לכם Cardcom דרך העמותה:

1. נכנסים לפאנל הניהול של Cardcom ומאתרים את **מספר הטרמינל**, **שם ה-API** וה**סיסמה** (בדרך כלל תחת הגדרות/מסופים/API — אם לא מוצאים, פונים לתמיכת Cardcom ומבקשים "פרטי חיבור API ל-LowProfile").
2. ממלאים ב-`.env`:
   ```
   CARDCOM_MOCK=false
   CARDCOM_TERMINAL_NUMBER=...
   CARDCOM_API_NAME=...
   CARDCOM_API_PASSWORD=...
   ```
3. **חשוב לדעת**: הקובץ `src/services/cardcom.js` מכיל כרגע רק שלד (stub) לקריאה האמיתית ל-API של Cardcom, מכיוון שבנייתו הסופית דורשת פרטי טרמינל אמיתיים לבדיקה מולם (שאין לי גישה אליהם). לפני מעבר לתשלומים אמיתיים יש להשלים את הקריאה בפועל לפי התיעוד הרשמי של Cardcom (`docs.cardcom.solutions`), ולבדוק מול סביבת הבדיקות (Sandbox) שלהם. אשמח להשלים את זה יחד ברגע שיהיו לכם פרטי הטרמינל מול Cardcom.
4. שימו לב: הוראת קבע חודשית אצל Cardcom בדרך כלל מחייבת אוטומטית כל חודש מצידם לאחר ההגדרה הראשונית — כדאי לוודא מולם איך מגיע אישור/כישלון חיוב חוזר (Webhook מהם), כדי לעדכן את הסטטוס (`status`) בטבלת `subscriptions` בהתאם (שדה קיים במסד, אך חיבור ה-Webhook הזה טרם נבנה).

### 5. אבטחה לפני עלייה לאוויר

- ב-`.env` הגדירו `JWT_SECRET` לערך אקראי וארוך (למשל תוצאה של `openssl rand -hex 32`) — לא את ברירת המחדל.
- ודאו שכתובת השרת רצה על HTTPS (רוב שירותי האחסון הנ"ל נותנים את זה אוטומטית).
- כדי להפוך משתמש למנהל מערכת (לצורך שינוי תמחור התוכניות), יש להריץ פעם אחת ידנית מול מסד הנתונים:
  ```bash
  node -e "require('./src/db.js').prepare(\"UPDATE users SET roles = roles || ',admin' WHERE username = 'שם_המשתמש_שלכם'\").run()"
  ```

## מגבלות ידועות והמלצות להמשך

- **חיבור Cardcom האמיתי טרם הושלם** (ר' סעיף 4 למעלה) — נדרשים פרטי טרמינל אמיתיים להשלמה ובדיקה.
- **ספק מייל אמיתי טרם נבחר** — עדכוני ההורים במייל (ר' סעיף "הורים" למעלה) פועלים כרגע במצב MOCK בלבד (`src/services/email.js`) ומודפסים ללוג במקום להישלח באמת. יש לבחור ספק (SendGrid/Postmark/SES/SMTP) ולמלא פרטי API לפני מעבר לייצור.
- הרשאות "תפקיד מקצועי" (mentor/therapist/supervisor) הן כרגע "הצהרה עצמית" חופשית שכל משתמש קובע לעצמו בהרשמה/בפרופיל — אין עדיין אימות שמישהו שמצהיר על עצמו כ"מטפל" באמת עובד עם העמותה. לשיוך הורה-ילד יש כבר הגנה (רק הבעלים משייך), אבל לתפקידי צוות עדיין לא. שווה לשקול בעתיד תהליך אישור ידני על ידי מנהל לפני שתפקיד מקצועי נכנס לתוקף, אם ההיקף יגדל.
- אין עדיין מסך ניהול (UI) לעדכון תמחור התוכניות — כרגע זה נעשה דרך קריאת API ישירה (`PUT /api/plans/:id`) על ידי משתמש עם תפקיד `admin`. אפשר להוסיף למסך "הגדרות אישיות" באב-הטיפוס בעתיד אם רוצים.
- אין עדיין קליטת Webhook מ-Cardcom לעדכון סטטוס חיוב חוזר חודשי (הצלחה/כישלון) — מומלץ להוסיף בשלב חיבור ה-API האמיתי.
