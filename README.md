# הפנקס שלי — שרת Backend

שרת אמיתי, פועל, לניהול תקציב אישי, חונכות, מעגל מטפלים, ומנוע שיחה קולית (IVR) בעברית חופשית — ללא לחיצת מקשים וללא SMS בשום מקום.

## למה אפס תלויות חיצוניות (0 packages)?

השרת נכתב כך שהוא רץ אך ורק עם היכולות המובנות של Node.js (גרסה 22 ומעלה) — ללא Express, ללא ספריות בסיס נתונים, ללא ספריות הצפנה חיצוניות. זה נבחר כדי שהקוד ירוץ בכל סביבה בלי תלות בזמינות רשת להתקנת חבילות, ובלי סיכוני אבטחה של תלויות צד-שלישי. בפועל:

| צורך | מה השתמשנו בו |
|---|---|
| שרת HTTP + ניתוב | `node:http` + נתב פשוט שכתבנו (`src/router.js`) |
| מסד נתונים | `node:sqlite` המובנה של Node (קובץ יחיד, בלי שרת נפרד) |
| הצפנת סיסמאות | `crypto.scryptSync` (שקול אבטחתית ל-bcrypt) |
| טוקן התחברות | JWT מינימלי שכתבנו לבד עם `crypto.createHmac` |
| קריאות לשירותים חיצוניים (Twilio, Cardcom) | `fetch` המובנה |

אפשר להוסיף בעתיד Express/PostgreSQL וכו' אם ירצו להרחיב, אך זה לא הכרחי — השרת כפי שהוא מוכן לעבודה אמיתית.

## הרצה מקומית (מצב בדיקה — בלי שום חשבון חיצוני)

```bash

node src/server.js
```

השרת יעלה על `http://localhost:3000`. בבדיקה ראשונית אפשר לפתוח בדפדפן `http://localhost:3000/api/health`.

כברירת מחדל הכול פועל **במצב MOCK**: שחזור סיסמה קולי ידפיס את הקוד ללוג וגם יחזיר אותו ב-API (`demoCode`) לבדיקה נוחה, וההצטרפות לתוכנית תרומה תיצור "הוראת קבע מדומה" בלי לחייב כרטיס אשראי אמיתי. כך אפשר לבדוק את כל המערכת מקצה לקצה בלי לשלם לאף אחד.

## הצגה מרחוק (למשל לחבר, בלי שהוא צריך להתקין משהו)

### הדרך הקלה - קובץ הפעלה אחד

בתיקיית `backend` יש קובץ בשם **`הפעלה-עם-לינק-לחבר.bat`**. לחיצה כפולה עליו פותחת אוטומטית שני חלונות - אחד עם השרת ואחד עם קישור השיתוף - בלי צורך להקליד פקודות בעצמכם. בחלון השני (שנקרא "קישור לחבר") תופיע שורה `your url is: https://...` - זו הכתובת ששולחים לחבר.

**חשוב:** שני החלונות שנפתחים חייבים להישאר פתוחים כל עוד רוצים שהקישור יעבוד. אם המחשב נכנס למצב שינה, או שסוגרים אחד מהחלונות בטעות, הקישור מפסיק לעבוד - פשוט הריצו את הקובץ שוב.

יש גם קובץ `הפעלה-מקומית.bat` שמפעיל רק את השרת (בלי קישור לחבר) - לשימוש רגיל במחשב עצמו.

### הדרך הידנית (אותו דבר, שלב-שלב)

השרת רץ רק על המחשב שלכם (`localhost`), אז כברירת מחדל אף אחד מבחוץ לא יכול להגיע אליו. כדי לשתף אותו זמנית עם מישהו אחר - בלי לפרוס שום דבר לענן - אפשר להשתמש ב"מנהרה" (tunnel) שיוצרת כתובת אינטרנט זמנית שמצביעה על המחשב שלכם:

1. משאירים את החלון שבו `node src/server.js` רץ **פתוח** (אל תסגרו אותו).
2. פותחים חלון PowerShell **נוסף** (חדש), נכנסים לתיקיית `backend`, ומריצים (ב-Windows, אם `npx` רגיל חסום ע"י מדיניות הרצת סקריפטים, יש להשתמש ב-`npx.cmd`):
   ```
   npx.cmd localtunnel --port 3000
   ```
   (בפעם הראשונה זה יוריד חבילה קטנה - זה תקין, אין צורך בהרשמה לשום שירות.)
3. תוך כמה שניות תופיע שורה עם כתובת כמו `your url is: https://short-name-12.loca.lt` - זו הכתובת ששולחים לחבר.
4. כשהחבר נכנס לכתובת הזו בפעם הראשונה, ייתכן שיראה מסך ביניים של השירות שמבקש ללחוץ "Click to Continue" (חד פעמי) - זה תקין ולא קשור לאפליקציה שלכם.

   בנוסף, כל מי שנכנס ללינק (גם אתם וגם החבר) עשוי להתבקש להזין "סיסמת מנהרה" - זה בדיוק כתובת ה-IP הציבורית של המחשב שממנו הוא נכנס. כל אחד מקבל אותה בעצמו על ידי כניסה מהמחשב שלו לכתובת https://loca.lt/mytunnelpassword (אי אפשר להעביר סיסמה אחת לכולם - לכל אחד יש ערך שונה, לפי הרשת שלו).
5. כשסוגרים את חלון ה-PowerShell של `localtunnel`, הכתובת מפסיקה לעבוד. הרצה חדשה של הפקודה נותנת כתובת אקראית חדשה בכל פעם.

### כתובת קבועה שלא משתנה בכל הרצה (מומלץ, כדי לא לשלוח לינק חדש כל פעם)

localtunnel מאפשר לבחור שם קבוע לכתובת בעצמכם, במקום שם אקראי, על ידי הוספת `--subdomain`:
```
npx.cmd localtunnel --port 3000 --subdomain hapinkas-sheli
```
זה ייתן כתובת קבועה: `https://hapinkas-sheli.loca.lt`. חשוב לדעת:
- זו לא הרשמה/הזמנה של השם - זה רק ניסיון לתפוס אותו בכל הרצה. אם מישהו אחר בעולם תופס בדיוק את אותו שם באותו רגע, תקבלו הודעת שגיאה ותצטרכו לבחור שם אחר (אפשר לשנות ל-`hapinkas-sheli-2` וכו').
- השם נשמר רק כל עוד המנהרה פתוחה - ברגע שסוגרים את החלון, השם משתחרר, וכל אחד (כולל אתם) יכול לתפוס אותו מחדש בפעם הבאה כרגיל.
- אם השם תפוס אצל מישהו אחר, זה בדרך כלל זמני - נסו שוב כעבור כמה דקות, או בחרו שם ייחודי יותר.

חשוב: כל עוד המנהרה פתוחה, מי שיש לו את הכתובת יכול לגשת למה שרואים ב-`http://localhost:3000` - כלומר לאותו מידע בדיוק שיש במסד הנתונים המקומי שלכם (כרגע מידע בדיקה בלבד). זה מתאים להדגמה מהירה וזמנית, לא כפתרון קבוע - למעבר אמיתי לייצור עם כתובת קבועה ראו את סעיף "מדריך פריסה לייצור" למטה.

## סקירת ה-API

כל הנתיבים המסומנים 🔒 דורשים כותרת `Authorization: Bearer <token>` שמתקבלת מהרשמה/התחברות.

| נתיב | תיאור |
|---|---|
| `POST /api/auth/signup` | הרשמה |
| `POST /api/auth/login` | התחברות |
| `POST /api/auth/forgot-password/request` | בקשת קוד שחזור (טלפון קולי או מייל) |
| `POST /api/auth/forgot-password/verify` | אימות הקוד |
| `POST /api/auth/forgot-password/reset` | קביעת סיסמה חדשה |
| 🔒 `GET/PUT /api/me` | פרופיל אישי (כולל הגדרת משך מפגש ברירת מחדל) |
| 🔒 `PUT /api/me/password` | החלפת סיסמה |
| 🔒 `GET/POST /api/transactions` | רשימת/הוספת תנועה, כולל סיכומים ופילוח קטגוריות |
| 🔒 `GET /api/transactions/dictionary?type=income\|expense` | "מילון" קטגוריות אישי להשלמה אוטומטית (datalist) - `type` ברירת מחדל `expense` |
| 🔒 `DELETE /api/transactions/:id` | מחיקת תנועה (תיקון טעות הזנה) - רק הבעלים, 404 לכל השאר |
| 🔒 `GET /api/transactions/trend` | מגמה חודשית לגרף |
| 🔒 `POST /api/transactions/import/parse` | ייבוא אקסל/CSV/PDF (דף בנק/כרטיס אשראי) - שלב 1: פירוק הקובץ + תצוגה מקדימה, לא שומר כלום (ר' סעיף ייעודי למטה) |
| 🔒 `POST /api/transactions/import/commit` | ייבוא אקסל/CSV/PDF - שלב 2: שמירת התנועות שאושרו, עם דילוג אוטומטי על כפילויות |
| 🔒 `GET/POST /api/students` | רשימת/הוספת תלמידים |
| 🔒 `POST /api/students/:id/checkin` \| `checkout` \| `quick-session` | שתי שיטות דיווח מפגש חונכות - `checkout`/`quick-session` מקבלים גם `note` אופציונלי (דיווח מעקב חופשי על המפגש) |
| 🔒 `POST /api/students/:id/lesson-reports` | טופס "הכנה לשיעור" (חונכות) - דיגיטציה של טופס נייר, כל השדות אופציונליים (ר' סעיף ייעודי למטה) |
| 🔒 `GET /api/lesson-reports/dictionary?kind=lesson_<שדה>` | "מילון" ניסוחים קודמים לכל שדה חופשי בטופס הכנה לשיעור |
| 🔒 `POST /api/students/:id/documents` | העלאת מסמך לתיק תלמיד (`title`, `filename`, `mime_type`, `data_base64`) |
| 🔒 `GET /api/students/:id/documents` | רשימת מסמכים של תלמיד - כותרות/מטא-דאטה בלבד, לא תוכן |
| 🔒 `GET /api/documents/:id/download` | הורדת תוכן מסמך ספציפי |
| 🔒 `DELETE /api/documents/:id` | מחיקת מסמך |
| 🔒 `GET /api/students/:id/file` | התיק המאוחד (מפגשים + דוחות + הערות + טופסי הכנה לשיעור + מסמכים בציר זמן אחד) — לבעלים/חונך/מטפל/מפקח בלבד |

| 🔒 `GET /api/reports/mine` | רשימת כל הדוחות שכתב איש המקצוע המחובר |
| 🔒 `GET /api/reports/dictionary?kind=note\|trend\|role_type\|session_note` | "מילון" ניסוחים אישיים קודמים (תוכן דיווח / מגמה / סוג דיווח / דיווח מעקב על מפגש חונכות) - להשלמה אוטומטית |
| 🔒 `POST /api/students/:id/guardians` | שיוך הורה לתלמיד (רק הבעלים/החונך יכול) |
| 🔒 `GET /api/students/:id/summary` | סיכום ידידותי להורה — מפגשים + דוחות בלבד, **בלי** הצ'אט הפנימי ו**בלי** הערות |
| 🔒 `GET /api/my-children` | רשימת הילדים שהמשתמש המחובר משויך אליהם כהורה |

**תוקן** (משוב אמיתי ממשתמש: "אני לא רואה שיש אפשרות למחוק נתונים"): נתיב המחיקה (`DELETE /api/transactions/:id`) כבר היה קיים בשרת, אבל לא היה חשוף בממשק בכלל - נוסף כפתור "מחיקה" לכל תנועה ברשימה (עמוד "תנועות"), עם חלון אישור לפני ביצוע.

**תוקן** (משוב אמיתי ממשתמש: "כשאני לוחץ על אחר אמור להיפתח קוביה לטקסט חופשי ולהשאיר קטגוריות למילון"): "אחר" ברשימת הצעות הקטגוריה (datalist בטופס "הוספת תנועה") היה עד עכשיו ערך רגיל כמו כל השאר - אם בחרו אותו, הוא נשמר כקטגוריה מילולית "אחר" ממש. עכשיו, בדיוק כמו "אחר" בתפריט הקטגוריות בטלפון (ר' למטה), בחירתו פותחת בקשה לטקסט חופשי (`prompt()`) - הטקסט שהוזן משמש כקטגוריה בפועל, ונכנס אוטומטית ל"מילון" האישי (אותו מנגנון `rememberPhrase`/`getDictionary` שכבר קיים) - יוצע גם באתר וגם בטלפון בפעם הבאה.

## מנוע השיחה הקולית — החלטה טכנית חשובה

בתכנון המקורי דיברנו על Twilio + Google Speech-to-Text בנפרד. בפועל, בזמן הבנייה גיליתי שהתג `<Gather input="speech" language="he-IL">` של Twilio עצמו מבצע זיהוי דיבור ומחזיר את התמלול ישירות ב-Webhook הבא — בלי צורך בהזרמת אודיו נפרדת ל-Google Cloud (מה שהיה דורש תשתית WebSocket מורכבת). לכן המנוע כאן משתמש רק ב-Twilio לזיהוי הדיבור. **המשמעות המעשית: יש רק ספק אחד לשלם ולהגדיר (Twilio), לא שניים.** זה מפשט את ההקמה ומוזיל את העלות החודשית לעומת מה שדיברנו עליו בהתחלה.

מכונת המצבים המלאה נמצאת ב-`src/routes/ivr.js`, עם קריאה חוזרת (read-back) ואישור "כן" לפני כל שמירה — בדיוק כמו באב-הטיפוס.

### תפריט הקטגוריות בטלפון

מיד כשהמערכת עונה, היא פותחת בברכת פתיחה קבועה: **"שלום וברכה, הגעתם לקו הפנקס שלי."** - ורק אחריה ממשיכה לשאר הדברים: **"שלום [שם], הגעתם לפנקס שלי. נא לציין לאיזה קטגוריה אתם רוצים להיכנס: ניהול חשבונות, תנועות, חונכות, מטפלים, הורה, או הערת מפקח."** - בלי צורך לומר "שלום" קודם או לחכות לצפצוף. אפשר גם לומר ישירות "הכנסה"/"הוצאה"/"יתרה" כקיצור דרך, בלי לעבור דרך הקטגוריה "תנועות"/"ניהול חשבונות" תחילה - המערכת סלחנית לשתי הדרכים. ברכת הפתיחה נאמרת **רק פעם אחת**, ממש בתחילת השיחה (גם אם המספר לא מזוהה ומוצעת הרשמה) - היא לא חוזרת שוב באמצע השיחה (למשל אחרי ביטול פעולה שחוזר לתפריט הראשי).

**בערוץ ימות המשיח בלבד** (ר' הסבר בהמשך למה רק שם), אפשר גם להקיש ספרה במקום לדבר - ובלי לחכות שהמערכת תסיים להקריא את כל התפריט: **1** לניהול חשבונות, **2** לתנועות, **3** לחונכות, **4** למטפלים, **5** להורה, **6** להערת מפקח, **7** למעשרות. אותו עיקרון פועל גם בתת-תפריטים - למשל בבחירת הכנסה/הוצאה/מעשרות (1/2/3), ובבחירת כניסה/יציאה/מפגש רגיל בחונכות (1/2/3).

**תוקן** (משוב אמיתי ממשתמש: "המערכת שואלת מה אתם רוצים... או להקיש 1 עד 7 - זה לא טוב, צריך לומר אפשר גם להקיש ניהול חשבונות 1, תנועות הקישו 2, וכן הלאה"): בעבר ברכת הפתיחה הקריאה את רשימת הקטגוריות ("ניהול חשבונות, או תנועות, או...") ורק **בסוף** הוסיפה הערה כללית נפרדת "אפשר גם להקיש 1 עד 7" - בלי לדעת איזו ספרה שייכת לאיזו קטגוריה, ההערה הזו לא הייתה שימושית בפועל. עכשיו (בימות בלבד) כל קטגוריה מקבלת את מספר ההקשה שלה **מיד אחריה**: "ניהול חשבונות הקישו 1. תנועות הקישו 2. חונכות הקישו 3." וכן הלאה - לא רשימה כללית מנותקת בסוף (`mainMenuCategoriesText` ב-`routes/ivr.js`).

**שאלות אישור "אישור/שינוי/ביטול"** (למשל אחרי אמירת סכום, לפני שמירת תנועה/דיווח/הערה) - **בימות בלבד**, אלה כבר **לא** שאלות זיהוי-דיבור בכלל: המערכת עוברת למצב הקשה טהור (בדיוק כמו קוד PIN) ולא מחכה לזיהוי דיבור/עיבוד קול כלל - תוקן בעקבות משוב אמיתי על שקט מיותר בין שלב לשלב, ועל כך שלא צריך לדבר בכלל בשלב הזה. שלוש אפשרויות בהקשה, בכל שאלת אישור כזו:
- **1** = אישור (שומר את הפריט)
- **2** = שינוי (חוזרים לשלב הקודם כדי להזין את הפריט מחדש - למשל שוב "כמה עלה?" - בלי לחזור עד לתפריט הראשי)
- **3** = ביטול מוחלט (חוזרים לתפריט הראשי, שום דבר לא נשמר)

(בעבר היה מודל בינארי 1=אישור/2=ביטול עם זיהוי דיבור כגיבוי ("אמרו כן לאישור") - הוחלף במלואו במודל המשולש הזה בעקבות משוב אמיתי. **ב-Twilio** (אין שם תמיכה בהקשות, ר' למטה) שאלות האישור נשארות מבוססות זיהוי-דיבור בלבד ("אמרו כן לאישור") - בלי אפשרות "שינוי" נפרדת שם.)

**תפריט קטגוריות הוצאה קבוע** - **בימות בלבד**, בחירת קטגוריית הוצאה (אחרי אמירת הסכום) עברה גם היא למצב הקשה טהור, בלי זיהוי דיבור כלל (משוב אמיתי: "לסדר בקטגוריות מזון/תחבורה... שיהיה רק עם הקשות"): **1** מזון, **2** תחבורה, **3** דיור, **4** בריאות, **5** חינוך, **6** ביגוד, **7** אחר (מוביל לתיאור חופשי בקול, כרגיל - אין דרך "לנחש" קטגוריה מותאמת-אישית בהקשה). ב-Twilio עדיין אפשר לומר את שם הקטגוריה בקול ישירות, בלי תפריט ממוספר.

**תפריט קטגוריות הכנסה, באותו עיקרון** (משוב אמיתי: "לגבי קטגוריות ניהול חשבונות... שיהיה עוד קטגוריות לאיזה הכנסה, ציינו ביטוח לאומי משכורת"): **1** משכורת, **2** ביטוח לאומי, **3** אחר (תיאור חופשי בקול, בדיוק כמו "אחר" בהוצאות - נשמר גם ל"מילון" הניסוחים האישי לפעם הבאה). ב-Twilio אפשר לומר את שם המקור בקול ישירות.

**כוכבית (\*) - חזרה לתפריט הראשי מכל מקום בשיחה** (ימות בלבד): בכל שלב בשיחה - תת-תפריט, שאלת אישור, בחירת תלמיד וכו' - הקשת כוכבית חוזרת מיד לתפריט הראשי, בלי לשמור שום דבר שהיה באמצע (בדיוק כמו לומר "לא"/"ביטול" בשאלת אישור, רק שזה עובד מכל מקום, לא רק בשאלת אישור). המכונה לא שומרת "היסטוריית תפריטים" לכל שלב, אז זו תמיד חזרה לתפריט **הראשי** - לא בהכרח לתפריט המיידי הקודם. לא פעיל בתוך התפריט הראשי עצמו (אין לאן "לחזור" משם), ולא בשלבי טקסט חופשי מוקלט (שם/שם תלמיד) - שם ימות חוסמת כל הקשה תוך כדי ההקלטה עצמה (מגבלה של ימות, לא קשורה לתכונה הזו).

**תוקן** (משוב אמיתי ממשתמש בבדיקה חיה: "קטגוריית ניהול חשבון חונכות השארת רק בזיהוי דיבור, אני צריך אופציה של הקשות"): בגרסה קודמת, כשזיהוי הדיבור המשודרג (Whisper, ר' הסעיף הייעודי למטה) היה מוגדר ופעיל, בחירת הקטגוריה בתפריט הראשי עצמו (וגם השלב אחרי קריאת יתרה - "רוצים להוסיף הכנסה או הוצאה") עברה למצב "הקלטה" נפרדת כדי לתמלל במדויק יותר - אבל אז הקשת ספרה לא נקלטה בכלל (מגבלת ימות: הקלטה גולמית חוסמת הקשות לגמרי). בפועל זה ביטל את קיצור ההקשה (1-6) בדיוק בשני השלבים שהכי משתמשים בו. **התיקון**: `main_menu` ו-`balance_next_action` (ר' `MENU_DIGIT_FREE_TEXT_STATES` ב-`src/routes/yemot.js`) כבר **לעולם לא** עוברים לשלוחת ההקלטה הנפרדת - הם תמיד נשארים במצב הזיהוי הרגיל של ימות (voice, עם `quiet_max` מכוון), כדי שקיצור ההקשה יישאר זמין תמיד, גם כש-Whisper פעיל. שאר שלבי הטקסט החופשי האמיתיים (שם בהרשמה, תוכן דיווח, שם תלמיד וכו') **כן** ממשיכים ליהנות מהדיוק המשופר של Whisper כרגיל - שם ממילא אין קיצור הקשה להפסיד. שאר קיצורי ההקשה (בתת-תפריטים ובשאלות אישור) **לא** מושפעים מכל זה ונשארים זמינים תמיד.

| קטגוריה | הקשה (ימות בלבד) | מוביל אל |
|---|---|---|
| ניהול חשבונות / חשבונות / יתרה | 1 | הקראת היתרה, ומיד אחריה שאלה אם להוסיף הכנסה/הוצאה (ר' למטה) |
| תנועות | 2 | שאלה "הכנסה או הוצאה?" ואז הזרימה הרגילה |
| חונכות | 3 | דיווח מפגש עם תלמיד (כניסה/יציאה/מפגש רגיל) |
| מטפלים | 4 | דיווח מקצועי (ריפוי בעיסוק/רגשי/אחר) |
| הורה | 5 | **סיכום קולי** על הילד/ים המשויכים (ר' סעיף ייעודי למטה) |
| הערת מפקח | 6 | הוספת הערה בתיק תלמיד |
| מעשרות | 7 | רישום מהיר של תשלום מעשר (ר' סעיף ייעודי למטה) |

**תוקן** (משוב אמיתי ממשתמש): "ניהול חשבונות" לא רק מקריא את היתרה וחוזר לתפריט הראשי הכללי - הוא שואל מיד **"רוצים להוסיף הכנסה או הוצאה, או לסיים? אפשר גם להקיש: 1 להכנסה, 2 להוצאה"**, בדיוק כמו שיש באתר. שימו לב שהמיפוי של 1/2 כאן הוא **מקומי לשלב הזה בלבד** (1=הכנסה, 2=הוצאה) ושונה מהמיפוי הרגיל של 1/2 בתפריט הראשי (1=ניהול חשבונות, 2=תנועות) - בדיוק כמו בתת-תפריט "תנועות" הרגיל. אפשר גם לומר/להקיש כל קטגוריה אחרת (למשל "חונכות") ישר משם, בלי לחזור קודם לתפריט הראשי במפורש.

**תוקן** (משוב אמיתי ממשתמש: "ששומעים מן היתרה... שיאמר מה סכום הכנסה ומה סכום הוצאות וחובת מעשרות"): קריאת היתרה כבר לא מסתפקת במספר הסופי (יתרה) - היא מקריאה גם את **סך ההכנסות**, **סך ההוצאות**, ו**חובת המעשר** (10% מסך ההכנסות, אותו חישוב בדיוק כמו בכרטיסיית "מעשרות" באתר, כולל הפחתת מה שכבר נרשם כהוצאה תחת הקטגוריה "מעשרות"). אם עדיין נותר משהו לתת - נאמר גם הסכום שנותר. כל פרט במשפט קצר ונפרד משלו (`חובת המעשר שלך היא X שקלים. נותרו לך Y שקלים לתת.`) ולא ברצף אחד עם פסיקים, לפי אותה הנחיה מפורשת על הפסקות שלא נתפסות בפסיק בטלפון.

### מעשרות - קטגוריה נפרדת מהכנסה/הוצאה, עם דיווח כמה כבר ניתן

בקשת פיצ'ר ממשתמש: "חוץ מהכנסה והוצאה, קטגוריה של מעשרות - שאפשר לומר או להקיש מעשרות, ואומר כמה מעשרות הוא נתן". מבחינת מסד הנתונים "מעשרות" הוא תמיד הוצאה עם `category='מעשרות'` (בדיוק כמו רישום דרך האתר - ר' הטיפ בעמוד "תנועות" שם), אבל בטלפון יש לו קיצור ייעודי משלו שמדלג ישר על שלב בחירת הקטגוריה (היא כבר ידועה מראש):

- **מהתפריט הראשי** - אומרים או מקישים "מעשרות" (הקשה **7**), ועוברים ישר לשאלת הסכום.
- **מתת-תפריט "תנועות"** - השאלה שם היא עכשיו **"הכנסה, הוצאה, או מעשרות?"** (הקשה: 1/2/3).

אחרי הסכום, שאלת אישור רגילה (1=אישור/2=שינוי/3=ביטול בימות, "אמרו כן" ב-Twilio - בדיוק כמו הכנסה/הוצאה). **בניגוד** לזרימת הכנסה/הוצאה הרגילה, אחרי השמירה **לא** מוצג תפריט "עוד/לעבור/לסיים" הממוקד - במקום זה מדווחים במפורש כמה מעשר ניתן (`נשמר. נתת X שקלים מעשר.`) וגם את הסך הכל שניתן עד כה (`סך הכל נתת עד כה Y שקלים מעשר.`), ואם רלוונטי גם כמה נותר לתת - **זה בדיוק מה שהמשוב ביקש** ("ואומר כמה מעשרות הוא נתן"), לא רק אישור שמירה גנרי. החישוב (`titheStatus()` ב-`routes/ivr.js`) משותף עם קריאת היתרה (`doBalance`) - אותו 10% מסך ההכנסות, בניכוי כל מה שכבר נרשם כהוצאה תחת "מעשרות".

### שיחה אחת, כמה פעולות - לא מנתקים מיד אחרי כל פעולה

בעבר, ברגע שפעולה הושלמה (הוצאה נשמרה, יתרה הוקראה, דיווח נשמר וכו') המערכת אמרה "תודה, להתראות" וניתקה מיד - כלומר כל שיחה יכלה לשרת רק פעולה אחת בלבד. עכשיו, אחרי כל פעולה (בכל הקטגוריות, בלי יוצא מן הכלל) המערכת שואלת **"רוצים לעשות עוד משהו, או לסיים?"** וחוזרת לתפריט הראשי - כך שאפשר למשל לשמוע יתרה, ומיד אחר כך להוסיף הוצאה, בלי לנתק ולהתקשר מחדש. כדי לסיים את השיחה בפועל, פשוט אומרים מהתפריט הראשי "תודה"/"לסיים"/"להתראות" (או דומה), והמערכת מנתקת בנימוס.

**תפריט המשך ממוקד אחרי שמירת הכנסה/הוצאה** (משוב אמיתי: "אחרי שכבר כתבתי וסימנתי הכנסה, המערכת צריכה לשאול: רוצים להוסיף עוד הכנסה או לעבור להוצאות? להוספה הקישו 1, לעבור להוצאה הקישו 2, לסיים הקישו 3") - במקום החזרה הכללית לתפריט הראשי, ספציפית אחרי שמירת תנועה (הכנסה או הוצאה) המערכת שואלת תפריט המשך ממוקד בן שלוש אפשרויות: **1** = עוד תנועה מאותו סוג (עוד הכנסה אחרי הכנסה, עוד הוצאה אחרי הוצאה) - ישר לשאלת הסכום הבאה, בלי לחזור לתפריט הראשי. **2** = לעבור לסוג השני (מהכנסה להוצאה, או להפך) - גם כן ישר לשאלת הסכום. **3** = לסיים - חוזר לתפריט הראשי הרגיל (ומשם אפשר לסיים את השיחה כרגיל). שאר הקטגוריות (יתרה, חונכות, מטפלים וכו') ממשיכות עם השאלה הכללית "רוצים לעשות עוד משהו, או לסיים?" כמתואר למעלה.

### קטגוריית "הורה" — סיכום קולי, בלי גישה לאתר

הורה שמספר הטלפון שלו רשום ומשויך לתלמיד (דרך `POST /api/students/:id/guardians`, בדיוק כמו בגישת האתר) יכול להתקשר ולומר "הורה", והמערכת תקריא לו סיכום: כמות המפגשים, סך הדקות, ומגמת הדיווח המקצועי האחרון - **אותו מידע בדיוק** שההורה רואה בכתב באתר (`GET /api/students/:id/summary`), רק מוקרא בקול. אם יש כמה ילדים משויכים, המערכת שואלת על איזה ילד לקרוא את הסיכום. אם אין ילדים משויכים, נאמר כך במפורש.

### הרשמה ישירות בטלפון

מספר טלפון לא מזוהה **לא מנותק מיד** - המערכת מציעה להירשם על המקום: שואלת שם מלא, ומיד ממשיכה (**בלי שאלת אישור נפרדת** - ר' "תוקן" למטה) לבקש **קוד PIN בן 4 ספרות** (ר' סעיף "קוד PIN" למטה). בסיום נוצר משתמש חדש עם מספר הטלפון שממנו התקשרו (Caller ID) ותפקיד ברירת מחדל "private". מיד אחרי ההרשמה עוברים ישר לתפריט הקטגוריות הרגיל, באותה שיחה.

**תוקן** (משוב אמיתי ממשתמש): בעבר, אחרי הכתבת השם, המערכת עוד שאלה "לאשר: נרשמים בשם X... אמרו כן" לפני שממשיכה - צעד כפול ומיותר. עכשיו ממשיכים ישר מהשם לקוד PIN - עדיין "חוזרים" על השם בתחילת המשפט הבא ("שלום X, עכשיו נגדיר קוד סודי...") כדי שיהיה ברור מיד מה נקלט, בלי לדרוש אמירת "כן" בנפרד.

**כתובת המייל - הוסרה לגמרי מזרימת ההרשמה הקולית (משוב אמיתי ממשתמש: "צריך לקצר... רק לומר מומלץ להוסיף מייל באתר ולהמשיך, בלי הקשות")**: בעבר (ר' היסטוריית הגרסאות למטה) ההרשמה בטלפון כללה שלב אינטראקטיבי שלם לכתובת מייל - הכתבה בקול, קריאה חוזרת לאישור, ותפריט הקשה לדילוג. זה כבר לא קיים. ברגע שקוד ה-PIN מאושר, ההרשמה מסתיימת **מיידית** עם משפט מידע קצר אחד ("...ונרשמת! מומלץ להוסיף כתובת מייל דרך האתר בהמשך - זה לא חובה.") וממשיכים ישר לתפריט הראשי - אין שום שאלה או הקשה בנושא המייל בטלפון יותר. מי שרוצה כתובת מייל בפרופיל (למשל לשחזור סיסמה בערוץ נוסף) מוסיף אותה באתר.

*היסטוריית הגרסאות הקודמות של שלב המייל הקולי (לפני שהוסר):* הגרסה הראשונה ביקשה מהמתקשר לבטא את כל הכתובת בקול - נכשלה כמעט תמיד מול מנוע הזיהוי הלא-משודרג של ימות. הגרסה השנייה ניסתה בניית כתובת אוטומטית מתעתיק השם + בחירת ספק בהקשה - בלבלה משתמשים בבדיקה חיה כי זו לא הייתה כתובת אמיתית. הגרסה השלישית עברה להכתבה מלאה דרך Whisper עם קריאה חוזרת ותפריט דילוג בהקשה - עבדה, אבל עדיין דרשה כמה צעדים אינטראקטיביים מיותרים להרשמה שכל מטרתה למהר. הוחלט לוותר על השלב כולו.

**חשוב להבין את מודל האבטחה כאן**: הזיהוי בטלפון **בשיחות רגילות** (גם למשתמש שנרשם בטלפון וגם למי שנרשם באתר) נשען תמיד על **מספר הטלפון שממנו מתקשרים (Caller ID)**, לא על הסיסמה/PIN - בדיוק כמו שבנק לא מבקש סיסמה כשמתקשרים מהמספר הרשום. קוד ה-PIN לא נשאל בשום שלב בשיחות הרגילות - הוא רק נקבע פעם אחת בהרשמה, ומשמש **בנפרד** להתחברות לאתר.

### קוד PIN - אותה סיסמה בדיוק לטלפון ולאתר

כל סיסמה במערכת (בין אם נקבעה באתר ובין אם הוקשה בטלפון) חייבת להיות **בדיוק קוד בן 4 ספרות** (ר' `isValidPin` ב-`src/utils/crypto.js`) - זו אותה מחרוזת בדיוק, אותו `password_hash`, בלי שדה נפרד ל"PIN טלפוני" מול "סיסמת אתר". זה נותן **הדדיות מלאה**: קוד PIN שהוקש בטלפון בהרשמה עובד ישירות כסיסמה להתחברות לאתר, וסיסמה שנבחרה באתר (אם היא כבר 4 ספרות) עובדת ישירות כקוד PIN. הסיבה לבחירה דווקא ב-4 ספרות ולא יותר: בטלפון אפשר רק להקיש ספרות במקלדת - סיסמה ארוכה או עם אותיות פשוט לא ניתנת להזנה אמינה בערוץ הזה.

**איך זה נקלט בטלפון**: בשלב קביעת ה-PIN בהרשמה, המערכת **לא** מנסה לזהות דיבור בכלל - היא עוברת למצב הקשת-מקלדת-בלבד (DTMF ב-Twilio, מצב "tap" בימות), בדיוק כמו הקשת קוד סודי בכספומט. הספרות **לא מוקראות בחזרה בקול** תוך כדי ההקשה (כדי שמי שנמצא ליד המתקשר לא ישמע את הקוד), ומתבקשים להקיש אותן פעם שנייה לאישור - אם ההקשה השנייה לא תואמת, מתחילים את קביעת ה-PIN מחדש (לא נשמר קוד שגוי בטעות).

**לגבי העיכוב שמורגש אחרי הקשת הספרות**: יש עיכוב טבעי (זמן תקשורת ברשת בין הטלפון לשרת, ובחזרה) בין רגע סיום ההקשה לבין שהמערכת עונה - זה קיים בכל מערכת IVR מבוססת-רשת, לא רק כאן. כדי שהמתקשר לא יישאר בספק אם ההקשה בכלל "נקלטה" בזמן ההמתנה השקטה, המענה הבא **תמיד פותח במילת אישור ברורה** ("התקבל...", "הקוד הוגדר בהצלחה...") - ברגע שהתשובה כן מגיעה, המילה הראשונה שלה כבר מבהירה שההקשה נקלטה. בנוסף, זמן ההמתנה בין הקשות בודדות (`sec_wait` במצב tap של ימות) קוצר ל-7 שניות (מ-15) כדי לא להאריך שום המתנה שלא לצורך.

**חשוב**: משתמשים קיימים עם סיסמה "ישנה" (שלא בפורמט 4 ספרות, מלפני התכונה הזו) ממשיכים להתחבר כרגיל - האכיפה חלה רק על סיסמה חדשה שנקבעת מעכשיו והלאה (הרשמה חדשה, שחזור סיסמה, או שינוי סיסמה בפרופיל). אם מישהו עם סיסמה ישנה רוצה שהיא גם תעבוד כ-PIN טלפוני, הוא צריך לשנות אותה (בפרופיל באתר, או דרך "שכחתי סיסמה") לקוד בן 4 ספרות.

**תוקן (משוב אמיתי: "ההדדיות לא עובדת")**: מספר טלפון הפך **לחובה** בהרשמה באתר (`POST /api/auth/signup`, ר' `src/routes/auth.js`) - קודם הוא היה אופציונלי, מה שבפועל שבר את ההדדיות: בלי טלפון שמור, אין שום דרך שהמשתמש יזוהה אי-פעם בשיחה נכנסת (הזיהוי תמיד לפי Caller ID), כלומר "הכיוון ההפוך" לא היה רלוונטי בפועל למי שנרשם באתר בלי למלא טלפון. עכשיו חובה, בדיוק כמו שם מלא/שם משתמש/סיסמה - גם בשרת (מחזיר 400 בלעדיו) וגם בטופס באתר עצמו (`public/app.html`, שדה `su_phone`).

### התחברות לאתר עם מספר טלפון (לא רק שם משתמש)

מי שנרשם ישירות בטלפון (ר' "הרשמה ישירות בטלפון" למעלה) מקבל שם משתמש אוטומטי (למשל `phone_501234567`) - אבל השם הזה **אף פעם לא נאמר לו בקול** (הזיהוי בטלפון עצמו תמיד לפי Caller ID, לא לפי שם משתמש). כדי שלא תיתקעו בלי לדעת מה להקליד בשדה "שם משתמש" באתר, אפשר **להתחבר גם עם מספר הטלפון עצמו** (בשדה "שם משתמש או מספר טלפון") יחד עם קוד ה-PIN שהוגדר בשיחה - זה עובד גם בהתחברות וגם בשחזור סיסמה (`findUserByLoginIdentifier` ב-`src/routes/auth.js`, מזהה כמה פורמטים נפוצים של אותו מספר, בדיוק כמו זיהוי המתקשר בשיחה עצמה). כמובן ששם המשתמש הרגיל ממשיך לעבוד גם הוא, לכל מי שמכיר אותו.

## חיבור קו "ימות המשיח" (טלפון "כשר" עם זיהוי דיבור)

בנוסף ל-Twilio, יש תמיכה בקו IVR2 של ימות המשיח (call2all.co.il) - מיועד למי שרוצה מספר "כשר" שעובר דרך רשתות סינון. זו **אינטגרציה עצמאית**, לא תלות ב-Twilio ולא ב-npm package חיצוני (`yemot-router2` וכדומה) - מימוש-יד לאותו פרוטוקול, כדי לשמור על עקרון "בלי ספריות חיצוניות" של הפרויקט. שתי האינטגרציות (`ivr.js` ל-Twilio, `yemot.js` לימות) חולקות **בדיוק** את אותה מכונת מצבים (`advance()` המיוצאת מ-`ivr.js`) - השינוי היחיד הוא שכבת התרגום לפרוטוקול.

### הגדרה בצד ימות המשיח

1. נכנסים לניהול המערכת בימות (`https://y-www.call2all.co.il` או מהקישור שקיבלתם באימייל ההרשמה) → **מערכת תוכן** → בוחרים שלוחה (למשל שלוחה 1) → **הגדרות מתקדמות**.
2. מחליפים את תוכן ה-`ext.ini` ל:
   ```
   type=api
   api_link=https://הכתובת-שלכם.onrender.com/api/ivr/yemot
   api_url_post=yes
   ```
   (מחליפים את הכתובת בכתובת השרת האמיתית שלכם - למשל `https://hapinkas-sheli-ze65.onrender.com/api/ivr/yemot`. **חשוב**: השדה נקרא `api_link`, לא `api_url` - זה השם המדויק שימות מצפה לו; `api_url` יגרום לשגיאת "לא הוגדר לינק".)
3. שומרים, ומתקשרים למספר המערכת לבדיקה.

### חשוב לדעת

- זיהוי המתקשר הוא לפי מספר טלפון (Caller ID), בדיוק כמו ב-Twilio - המשתמש חייב להיות רשום במערכת עם מספר הטלפון שממנו הוא מתקשר.
- ימות שולח את מספר המתקשר בפורמט מקומי (`0501234567`) בעוד ש-Twilio שולח פורמט בינלאומי (`+972501234567`) - השרת מזהה אוטומטית את שתי הצורות (`findUserByPhone` ב-`src/routes/yemot.js`), כך שאותו משתמש רשום מזוהה משני הספקים בלי הגדרה נוספת.
- הקלט מהמתקשר מתקבל בעיקר ע"י זיהוי דיבור (`stt`), אבל **בניגוד ל-Twilio, ימות לא חוסמת לחיצת מקשים תוך כדי זיהוי הדיבור** - ולכן כאן (ורק כאן) יש גם קיצורי הקשה (ר' "תפריט הקטגוריות בטלפון" למעלה): ספרות לניווט בתפריט, שאלות אישור במצב הקשה טהור (1=אישור/2=שינוי/3=ביטול, בלי זיהוי דיבור בכלל), וכוכבית לחזרה מיידית לתפריט הראשי מכל מקום בשיחה. ב-Twilio, ה-`<Gather>` מוגדר `input="speech"` בלבד ולכן אין שם תמיכה בהקשות.
- לשלבים שמבקשים **טקסט חופשי גרידא** ואין בהם שום קיצור הקשה בעל משמעות (כרגע: שם מלא בהרשמה, שם תלמיד בחונכות, וסכום הכנסה/הוצאה/מקור הכנסה מותאם-אישית) - `sayAndReadStt(text, { freeText: true })` ב-`src/services/yemot.js` עובר למנוע "הקלטה" (`use_records_recognition_engine`) של ימות במקום מצב ה-`voice` הרגיל, כדי לאפשר לכוון `quiet_max` (כמה שניות שקט לפני שנחשב שסיימו לדבר - 3 שניות, במקום ברירת המחדל הקצרה של ימות שנוטה "לחתוך" שם דו-מילתי). **חשוב**: הקשת ספרות/סולמית תוך כדי ההשמעה נחסמת אוטומטית במצב הזה (מגבלה של ימות עצמו) - ולכן זה מופעל רק בשלבים שממילא אין בהם קיצור הקשה שימושי (`FREE_TEXT_STATES` ב-`src/routes/yemot.js`).
- אם השיחה לא מזוהה, המערכת עונה בקול ומנתקת בצורה מסודרת (לא "תקלה" סתומה).
- אם שיחה חוזרת ממספר שכבר נרשם "לא מזהה" אתכם ומציעה להירשם שוב - כמעט תמיד הסיבה היא שההרשמה הקודמת לא הושלמה עד הסוף (למשל נותקתם/הפסקתם באמצע, לפני שאמרתם "כן"/הקשתם על שאלת האישור הסופית) - במקרה כזה המשתמש החדש פשוט לא נוצר בפועל. אפשר לוודא זאת בלוח הבקרה של Render (`Logs`), או פשוט לנסות להירשם שוב מההתחלה.

### זיהוי דיבור משודרג (ימות המשיח + OpenAI Whisper) — אופציונלי

מנוע זיהוי הדיבור המובנה של ימות המשיח (הנ"ל למעלה) עובד היטב לרוב, אבל בבדיקות בפועל התברר שהוא מתקשה במיוחד עם **שמות אנשים** ו**סכומי כסף** - לפעמים "חותך" שם דו-מילתי (למשל "יוסף לוי") באמצע, לפעמים פשוט לא מזהה סכום בכלל (**תוקן**, ר' משוב אמיתי למטה), או לא מזהה בכלל אחרי כמה ניסיונות. אפשר (לא חובה) לשדרג את זיהוי הדיבור **רק** בשלבי שם/טקסט חופשי (`FREE_TEXT_STATES` ב-`src/routes/yemot.js` - כרגע: תפריט הראשי, שאלת "עוד הכנסה/הוצאה" אחרי יתרה, שם מלא בהרשמה, שם תלמיד בחונכות, וסכום הכנסה/הוצאה/מקור הכנסה מותאם-אישית) על ידי החלפת מנוע הזיהוי של ימות בתמלול משלנו, מדויק בהרבה, באמצעות **Whisper** של OpenAI.

**תוקן** (משוב אמיתי ממשתמש: "נכנסתי, הכנסה, אמרתי 100 ש"ח והוא לא זיהה") - סכום הכנסה/הוצאה עד אז לא היה ב-`FREE_TEXT_STATES` בכלל, כך שהזיהוי תמיד עבר דרך מנוע הזיהוי המובנה החלש יותר של ימות (לא Whisper), בדיוק כמו שהיה עם התפריט הראשי לפני שתוקן. בנוסף, גם מנוע זיהוי דיבור טוב עלול "לכתוב" מספר שנאמר בקול כמילה ("מאה") ולא כספרות ("100") - נוספה רשת ביטחון נוספת: אם אין ספרות בטקסט, המערכת מנסה לפענח מילות מספר בעברית (`parseHebrewNumberWords` ב-`src/routes/ivr.js` - מכסה יחידות, עשרות, מאות, ואלפים, למשל "מאתיים וחמישים" -> 250), כך שגם אם התמלול (בכל מנוע) כותב את המספר במילים, הסכום עדיין מזוהה.

**איך זה עובד (ארכיטקטורה נוכחית - שלוחת הקלטה נפרדת):** בשלבים האלה בלבד, המערכת מעבירה את השיחה **זמנית** לשלוחה נפרדת מסוג `type=record` שמגדירים בממשק הניהול של ימות (ר' "הגדרת שלוחת ההקלטה" למטה) - שלוחה שכל תפקידה הוא להקליט ולשמור את ההקלטה בוודאות, ואז להעביר את השיחה בחזרה אוטומטית לשלוחת ה-API שלנו (`record_end_goto`). ברגע שהשיחה חוזרת, המערכת מורידה בעצמה את ההקלטה האחרונה מהשרתים של ימות ושולחת אותה ל-Whisper לתמלול. שאר השיחה (תפריטים, קיצורי הקשה, שאלות אישור וכו') ממשיכה לעבוד בדיוק כמו היום, בלי שינוי.

**סטטוס נוכחי: שינוי ארכיטקטורה, טרם נבדק מול קו אמיתי.** ניסיון קודם - להקליט "בתוך" שלוחת ה-API עצמה (מצב `record` בפרוטוקול ה-`read=`) - נבדק שוב ושוב מול קו אמיתי ומעולם לא הצליח בפועל (ההקלטה מעולם לא נשמרה, ר' `GetIVR2Dir`), למרות כמה ניסיונות תיקון פרמטרים. עברנו לארכיטקטורה **מוכחת-בשטח** שמפתחים אחרים משתמשים בה בהצלחה: שלוחה נפרדת ייעודית להקלטה, עם מעבר-שיחה מפורש (`go_to_folder`) במקום לנסות "להקליט מבפנים". **חשוב להיות כנים**: גם הצעד הזה עוד לא מתועד באופן מלא ורשמי (למשל, לא ברור לגמרי אם מזהה השיחה `ApiCallId` נשאר זהה במעבר בין השלוחות - הוספנו מנגנון גיבוי שמזהה מחדש לפי מספר טלפון למקרה שלא) - יכול להיות שיידרש עוד ניסוי-וטעייה קטן בשיחה אמיתית אחת-שתיים לפני שזה עובד חלק לגמרי. כדי לכבות זמנית בכל שלב וחזרה מיידית להתנהגות הקודמת (זיהוי הדיבור הרגיל של ימות) - משנים את `WHISPER_RECORD_MODE_ENABLED` ל-`false` ב-`src/routes/yemot.js`.

**חשוב לדעת לפני שמפעילים:**
- זו תוספת **אופציונלית לגמרי** - כל עוד לא מגדירים את ארבעת המפתחות למטה (כולל `YEMOT_RECORD_EXTENSION` החדש), המערכת ממשיכה לעבוד בדיוק כמו היום (מנוע הזיהוי הרגיל של ימות), בלי שום שינוי בהתנהגות.
- **כן, יש לזה עלות כספית מול OpenAI** - תשלום לפי שימוש בפועל, דורש כרטיס אשראי/חשבון OpenAI פעיל. לפי [תיעוד המחירים הרשמי של OpenAI](https://developers.openai.com/api/docs/pricing) (נבדק אוגוסט 2026), המודל שבו המערכת משתמשת (`whisper-1`) עולה כ-**0.006$ לדקת הקלטה** (כ-2.2 אגורות לדקה, לפי שער דולר משוער). ההקלטות כאן קצרות מאוד (שם או מילת קטגוריה, עד 15 שניות כל אחת) - כלומר **עלות של שברירי אגורה לשיחה בודדת**. גם בהיקף שימוש סביר לעמותה (מאות שיחות בחודש) מדובר בסכום זניח - אבל זו החלטה כספית שלכם, לא רק טכנית, אז חשוב לדעת את המספרים לפני שמפעילים. (**תוקן**: המודל שונה מ-`gpt-4o-mini-transcribe` הזול יותר ל-`whisper-1` - ר' "בעיה שהתגלתה בבדיקה חיה" למטה, סיבה טכנית ולא רק מחיר.)
- **מגבלה ידועה**: שלוחת ההקלטה הנפרדת משותפת לכל השיחות בו-זמנית - אם שני אנשים מתקשרים ומדברים בדיוק באותם רגעים, המערכת עלולה לבלבל בין ההקלטות שלהם (בוחרים תמיד את ה"חדשה ביותר" בתיקייה). בהיקף שיחות קטן-בינוני (עמותה) זה מצב קצה נדיר, אבל כדאי לדעת שהוא קיים.

### הגדרת שלוחת ההקלטה בימות (`type=record`) - שלב חד-פעמי בממשק הניהול

כדי שהתכונה תעבוד, בנוסף להגדרת שלוחת ה-API הרגילה (למעלה), צריך גם שלוחה **נפרדת** (מספר שונה, למשל שלוחה 2 - כל עוד היא לא בשימוש) שתוקדש רק להקלטה:

1. נכנסים לניהול המערכת בימות → **מערכת תוכן** → בוחרים שלוחה פנויה (למשל שלוחה `2`, שממילא מוצגת כברירת מחדל "השמעת קבצים" אם לא נעשה בה שימוש) → **הגדרות מתקדמות**.
2. מחליפים את תוכן ה-`ext.ini` שלה ל (מחליפים `/1` במספר שלוחת ה-API האמיתית שלכם, אם היא לא 1):
   ```
   type=record
   say_record_menu=no
   record_ok=#
   record_end_goto=/1
   option_record=3-1-60
   ```
   (`record_ok=#` = הקשת סולמית מאשרת ושומרת את ההקלטה; `record_end_goto=/1` = אחרי האישור, חוזרים אוטומטית לשלוחת ה-API; `option_record=3-1-60` = 3 שניות שקט נחשבות "סיימו לדבר", הקלטה של 1-60 שניות.)

   **עדכון חשוב** (אם כבר הגדרתם את השלוחה הזו קודם עם `option_record=3-1-15`): צריך **לעדכן** את הערך ל-`3-1-60` - 15 שניות מספיקות לשם/קטגוריה/סכום קצרים, אבל לא מספיקות לדיווח מטפל או הערת מפקח (תוכן חופשי וארוך יותר) שגם הם עכשיו עוברים דרך אותה שלוחת הקלטה - ר' "הרחבת זיהוי הדיבור המשודרג לכל השלבים" למטה. שדות קצרים לא נפגעים מההגדלה (הם ממילא מסתיימים מוקדם יותר בזכות 3 שניות השקט).
3. שומרים. **אין צורך ליצור שלוחה חדשה** - משתמשים במספר קיים שלא בשימוש.
4. ב-Render, מוסיפים משתנה סביבה חדש: `YEMOT_RECORD_EXTENSION` עם מספר השלוחה שבחרתם (למשל `2`).

**חשוב**: המפתחות `record_ok`/`record_end_goto`/`option_record` מבוססים על מחקר בתיעוד ובקוד פתוח, אבל **לא אומתו עדיין מול הממשק שלכם בפועל** - ייתכן שימות דורשת ניסוח מעט שונה. הדרך הכי מהירה לבדוק אם זה עובד: מתקשרים, מגיעים לשלב שאמור להעביר לשלוחת ההקלטה (למשל שם בהרשמה), ואם אחרי שאומרים משהו וממתינים השיחה חוזרת בחלקה לתפריט הרגיל (ולא נתקעת/מתנתקת) - זה סימן טוב. אם משהו לא עובד כצפוי - אפשר לבדוק את `/api/debug/yemot-dir?key=hapinkas-diag-9427&path=<מספר-שלוחת-ההקלטה>` כדי לראות אם ההקלטה בכלל נשמרת שם.

**כלי אבחון זמני**: אפשר לבדוק ישירות, בלי לדפדף באתר הניהול של ימות, אילו קבצים נשמרים בשלוחת ההקלטה: לפתוח בדפדפן את הכתובת `https://<כתובת-השירות-שלכם>/api/debug/yemot-dir?key=hapinkas-diag-9427&path=<מספר-שלוחת-ההקלטה>`. זה יחזיר רשימת קבצים בפורמט טכני (JSON) - אם רשימת ה-`files` ריקה, ההקלטה לא נשמרת בכלל אצל ימות (הבעיה בהגדרות ה-`ext.ini` של שלוחת ההקלטה); אם יש שם קבצים, ההקלטה כן נשמרת וזה כבר סימן חיובי. **יש להסיר את הנתיב הזה מהקוד אחרי שהכל יעבוד בבטחה** (הוא לא מוגן בסיסמה אמיתית, רק במילת-מעבר קבועה בכתובת).

### בעיה שהתגלתה בבדיקה חיה (ותוקנה): תמלול "מוזה" לכתב לא-עברי

בבדיקת טלפון אמיתית ראשונה עם הארכיטקטורה החדשה, שלב ההעברה לשלוחת ההקלטה **עצמו עבד מצוין** - ההקלטה נשמרה, ירדה, ותומללה. אבל התגלתה בעיה אמיתית ומפתיעה במודל התמלול עצמו: המודל `gpt-4o-mini-transcribe`, למרות שהתבקש בפירוש לתמלל בעברית (`language=he`), "המציא" (hallucinate) לפעמים תמלול בכתב **שאינו עברי בכלל**. באותה מילה בדיוק ("חונכות"), בשלוש שיחות שונות, המודל החזיר שלוש תוצאות שונות - פעם באותיות לטיניות ("Conchód"), פעם קיריליות ("Холхот"), פעם ערביות ("خونخود") - אף פעם לא בעברית עצמה. גם שם ("שלום שטיינברג") תומלל נכון מבחינת התוכן, אבל בכתב לטיני ("Shalom Steinberg") ולא בעברית. תוצאה בפועל: הקטגוריה בתפריט הראשי מעולם לא הצליחה להתאים לאף מילה מוכרת, והשיחה "נתקעה" בלולאת "לא הבנתי, נסו שוב" עד לניתוק.

**מה תוקן**: (1) המודל הוחלף מ-`gpt-4o-mini-transcribe` ל-`whisper-1` - מודל ותיק ובוגר יותר, שנבדק במשך שנים במיוחד על תמלול רב-לשוני, ונחשב אמין יותר לשפות שאינן אנגלית מהגרסאות ה"4o" החדשות והמהירות. (2) נוסף "רמז אוצר מילים" (`prompt` בבקשה ל-Whisper) שמותאם לשלב הנוכחי בשיחה - למשל בתפריט הראשי מעבירים את רשימת הקטגוריות המדויקת ("ניהול חשבונות, תנועות, חונכות...") כדי להטות את התמלול לכיוון המילים שבאמת צפויות שם. (3) **רשת ביטחון**: אם בכל זאת מתקבל תמלול בלי אף אות עברית אחת - המערכת מתייחסת לזה כאילו נכשל (במקום לנסות להשתמש בטקסט חסר-משמעות), כך שהמתקשר יתבקש לנסות שוב במקום שהשיחה "תיתקע" בשקט. **שימו לב**: גם עם התיקון הזה, מודלי תמלול הם לא דטרמיניסטיים לגמרי - אותה הקלטה בדיוק יכולה מדי פעם להיות מתומללת קצת אחרת בין ניסיון לניסיון. הציפייה הסבירה היא שיפור משמעותי בשיעור ההצלחה, לא אפס טעויות.

### בעיה שנייה שהתגלתה (ותוקנה): "אימוץ שיחה" שגוי גרם ל"תקיעות" אחרי ניתוק וחיוג חוזר

בבדיקה נוספת התברר עוד באג אמיתי, חמור יותר מבחינת החוויה: מנגנון "אימוץ שיחה לפי טלפון" (`reattachRecordingCall` ב-`routes/yemot.js` - נועד להתמודד עם האפשרות ש-`ApiCallId` משתנה בין שלוחות, ר' למעלה) היה **רחב מדי** - הוא ניסה "לאמץ" גם את בקשת ה**פתיחה** הראשונה של חיוג חדש לגמרי (לפני שהמתקשר בכלל הגיע לשלוחת ה-API). כשמתקשר ניתק תוך כדי שהשיחה עדיין הייתה "ממתינה להקלטה" (`_recording:true`) וחייג שוב תוך פחות מ-3 דקות, החיוג ה**חדש** לגמרי "נחטף" בטעות לתוך השיחה הישנה והתקועה - במקום לקבל ברכת פתיחה נקייה, המערכת ניסתה לתמלל שוב את ההקלטה **הישנה** מהניסיון הקודם. זה בדיוק מה שגרם לתחושת "אני אומר את המילה, המערכת קולטת (הקלטה ישנה!) אבל לא ממשיכה נכון".

**מה תוקן**: (1) "אימוץ שיחה" מנסה להתבצע **רק** אם בבקשה יש `ApiExtension` (כלומר זו לא ממש בקשת הפתיחה הראשונה של חיוג) - כך שחיוג חדש לגמרי תמיד יתחיל נקי, בלי סיכון "לחטוף" שיחה ישנה. (2) בכל ניתוק (`hangup=yes`) המערכת עכשיו **מנקה** את הדגל `_recording` מהשיחה שהסתיימה, כך ששיחה שהמתקשר ניתק ממנה לעולם לא תיאמץ בטעות ע"י חיוג עתידי. (3) כרשת ביטחון נוספת, גם צומצם החלון הזמן לאימוץ מ-3 דקות ל-90 שניות. **טרם נבדק שוב מול קו אמיתי** - כדאי לבדוק שוב, ובמיוחד לבדוק שגם אחרי ניתוק וחיוג חוזר מיידי מתקבלת ברכת פתיחה רגילה ולא המשך "מוזר" של השיחה הקודמת.
- **חשוב להבין: זה משפר דיוק, לא מהירות** - אם כבר יש תחושה שהמערכת "לוקחת זמן" לענות (למשל בין שאלות), הפעלת התכונה הזו **לא** תפתור את זה ועלולה אפילו להאט מעט את השלבים שבהם היא פעילה (יש בהם שתי קריאות רשת נוספות - הורדת ההקלטה מימות, ואז שליחתה ל-Whisper - לפני שאפשר להמשיך). התועלת שלה היא זיהוי מדויק יותר של שמות שנאמרים בקול, לא תגובה מהירה יותר.

**שלבי הפעלה (ארבעה מפתחות, כולם צריכים להיות מוגדרים יחד ב-Render כדי שהתכונה תופעל):**

1. **מפתח API קבוע של ימות המשיח** (לא סיסמת ההתחברות הרגילה שלכם!) - נכנסים לניהול המערכת בימות, **הגדרות פיירוול** (או "הגדרות מתקדמות" → "API", בהתאם לגרסת הממשק), ויוצרים שם "מפתח API" חדש. מעתיקים את הערך שמתקבל (בדרך כלל בפורמט כמו `0501234567:xxxxxxxxxx`) - זה יהיה `YEMOT_API_TOKEN`.
2. **מספר השלוחה שלכם (שלוחת ה-API הרגילה)** - אותו מספר שכבר מצאתם/הגדרתם בסעיף "הגדרה בצד ימות המשיח" למעלה (למשל `1`) - זה `YEMOT_EXTENSION_NUMBER`.
3. **מספר שלוחת ההקלטה הנפרדת** - המספר שבחרתם והגדרתם בסעיף "הגדרת שלוחת ההקלטה" למעלה (למשל `2`) - זה `YEMOT_RECORD_EXTENSION`.
4. **מפתח API של OpenAI** - נרשמים בכתובת `https://platform.openai.com` (אם עדיין אין חשבון), ויוצרים מפתח חדש בכתובת `https://platform.openai.com/api-keys`. מעתיקים את הערך (מתחיל ב-`sk-`) - זה `OPENAI_API_KEY`. **שימו לב**: אחרי יצירת המפתח לא ניתן לראות אותו שוב, רק להעתיק מיד ולשמור במקום בטוח.
5. נכנסים ללוח הבקרה של Render → השירות שלכם → **Environment** → מוסיפים ארבעה משתני סביבה חדשים: `YEMOT_API_TOKEN`, `YEMOT_EXTENSION_NUMBER`, `YEMOT_RECORD_EXTENSION`, `OPENAI_API_KEY` (עם הערכים מהשלבים למעלה) - **לא** צריך לגעת ב-`WHISPER_MOCK` בכלל (ר' הערה למטה). שומרים - Render יפרוס מחדש אוטומטית עם המשתנים החדשים.
6. מתקשרים למספר ומגיעים לשלב שאומרים בו שם (למשל הרשמה, או "יש תלמיד חדש") - ובודקים שזה עובד כרגיל. אפשר לבדוק בלוח הבקרה של Render (`Logs`) שורות שמתחילות ב-`[WHISPER-DEBUG]` כדי לראות בדיוק מה הורד ומה תומלל, בדיוק כמו ש-`[YEMOT-DEBUG]` עוזר לאבחן את שאר השיחה.

הערה לגבי `WHISPER_MOCK` שמופיע ב-`.env.example`: זהו רק תיעוד לברירת המחדל (המערכת "שקטה" כל עוד לא הוגדרו ארבעת המפתחות למעלה) - אין צורך להגדיר אותו בפועל בשום שלב, לא בבדיקות ולא בייצור.

### הרחבת זיהוי הדיבור המשודרג לכל השלבים (לא רק תפריט/שם/סכום)

**תוקן** (משוב אמיתי ממשתמש: "אותו הדבר תעשה בכל הקטגוריות, לא רק הכנסה והוצאה") - אותה בעיה בדיוק (מנוע הזיהוי המובנה של ימות חלש יחסית) קיימת עקרונית בכל שלב שמצפה לתשובה חופשית/שם ולא רק להקשת ספרה. עכשיו זיהוי הדיבור המשודרג (Whisper) פעיל גם בשלבים הבאים, בנוסף לתפריט הראשי/שם/סכום שכבר תוקנו קודם:

- **קטגוריית הוצאה מותאמת-אישית** ("אחר", ר' `expense_category_other`) - תיאור חופשי, אחרי שהקטגוריות הקבועות (מזון/תחבורה/וכו') עברו בהמשך למצב תפריט-הקשה קבוע (ר' "תפריט הקטגוריות בטלפון" למעלה - משוב אמיתי מאוחר יותר: "רק עם הקשות, לא זיהוי דיבור").
- **סוג דיווח מטפל** (ריפוי בעיסוק/טיפול רגשי/אחר) - חשוב במיוחד: קלט לא מזוהה כאן נופל **בשקט** ל"אחר" בלי אף הודעת "לא הבנתי" (בשונה מהתפריט הראשי) - כך שדיוק התמלול קריטי במיוחד.
- **שם תלמיד** בדיווח מטפל, בהערת מפקח, ובבחירת ילד להורה עם כמה ילדים - אותו דפוס בדיוק כמו שם תלמיד בחונכות (שכבר תוקן קודם).
- **תוכן דיווח מטפל / הערת מפקח / 4 שדות טופס "הכנה לשיעור" בטלפון** (ר' "גרסה מקוצרת בטלפון" למעלה) - תוכן חופשי וארוך יותר (משפט-שניים, לא מילה בודדת). **דורש** את עדכון `option_record` בשלוחת ההקלטה מ-`3-1-15` ל-`3-1-60` (ר' "הגדרת שלוחת ההקלטה" למעלה) - אחרת תוכן ארוך עלול להיחתך אחרי 15 שניות בלבד.

**מה בכוונה נשאר כמו שהיה** (לא עבר ל-Whisper): שלבים עם קיצורי הקשה קיימים ואמינים - בחירת הכנסה/הוצאה בתת-תפריט "תנועות" (1/2), בחירת כניסה/יציאה/מפגש רגיל/הסרה בחונכות (1/2/3/4), אישור הוספת תלמיד חדש (1/2), ושאלות כן/לא בכלל (יש בהן כבר קיצור הקשה 1/2 אמין) - מעבר ל-Whisper שם היה **חוסם** את קיצורי ההקשה האלה (מצב "הקלטה" לא קולט הקשות בכלל), בלי שום תועלת מתאימה מולם.

## חונכות — דיווח מעקב חופשי על מפגש

בנוסף למשך המפגש (שנקבע אוטומטית ב-checkin/checkout, או ידנית ב-quick-session), החונך יכול עכשיו לצרף `note` אופציונלי - דיווח מעקב חופשי (למשל "עבדנו על חיבור וחיסור, התקדמות יפה") - שנשמר יחד עם המפגש (`sessions.note`), מופיע בתיק המאוחד (`/file`), **וגם** מוצג להורה בסיכום (`/summary`), בדיוק כמו דוחות המטפלים. גם כאן פועל אותו "מילון" ניסוחים אישי (`kind=session_note`) להשלמה אוטומטית לתלמידים הבאים.

**עדכון (בעקבות בקשת פיצ'ר): אותו דיווח מעקב אפשר להכתיב עכשיו גם בטלפון**, לא רק באתר. מיד אחרי "יציאה" (checkout) או "מפגש רגיל" (quick-session) בקטגוריית "חונכות", המערכת שואלת "רוצים להוסיף גם דיווח מעקב חופשי על המפגש? זה לא חובה" - עם קיצור הקשה אמין 1=כן/2=לא (לא Whisper, כדי שתמיד אפשר לדלג בביטחון). מי שעונה כן מתבקש להכתיב את הדיווח בקול (עובר דרך אותו מנגנון תמלול Whisper כמו דיווח מטפל/הערת מפקח - ר' "הרחבת זיהוי הדיבור המשודרג" למעלה), שומע אותו מוקרא בחזרה לאישור, ואז הוא נשמר על אותו מפגש בדיוק (`sessions.note`) ונכנס גם ל"מילון" הניסוחים האישי - בדיוק כמו דיווח שמוזן באתר. שים לב: אין הצעת דיווח אחרי "כניסה" (checkin) בלבד - שורת ה-`sessions` נוצרת רק בסיום המפגש (checkout), אז ההצעה מגיעה שם.

## חונכות — טופס "הכנה לשיעור" (דיגיטציה של טופס נייר)

`POST /api/students/:id/lesson-reports` הוא דיגיטציה של טופס נייר שהועבר בתהליך הבנייה, בנוסף למפגש הרגיל. כל השדות אופציוניים ובניסוח חופשי - הטבלה `lesson_reports` (`src/db.js`) והראוט `src/routes/lessonReports.js` שומרים בדיוק את מבנה הכותרות מהטופס המקורי: תאריך (אפשר גם עברי, כמו "יג כסלו"), שם/טלפון/שעות נוחות של המלמד, ימי לימוד, תאריך הדרכה + המלצה/תאריך להערכה חוזרת, מס' שבוע/פגישה/זמן לימוד, הקטע הנלמד בשיעור, מטרה, צורת עבודה, יישום בפועל, התחברות ושיתוף פעולה, התמודדות והשגת המטרות, הערות מהסביבה, איחורים וחיסורים.

בלוח הבדיקה, שדות שם/טלפון המלמד מתמלאים אוטומטית מהפרופיל של המשתמש המחובר (נוח, לא "שם קשיח") - ואפשר לערוך אותם. לכל שדה חופשי פועל אותו "מילון" ניסוחים אישי שכבר קיים במערכת (`kind=lesson_<שם השדה>`, למשל `lesson_topic_studied`) - הטופס מוצע להשלמה אוטומטית לתלמידים הבאים, בלי לשכפל ניסוחים מהתלמיד/הטופס הספציפי. הטופס מופיע בתיק המאוחד (`/file`) **וגם** בסיכום שההורה רואה (`/summary`) - מלבד טלפון/שעות נוחות של המלמד, שאינם רלוונטיים להורה.

### גרסה מקוצרת בטלפון (ימות בלבד) - 4 שדות, לא כל הטופס

אחרי "מפגש רגיל" בחונכות (`doQuickSession`, **לא** אחרי checkin/checkout) - מוצעת גם אפשרות למלא בקצרה 4 מתוך שדות הטופס: **הקטע שנלמד, המטרה, היישום בפועל, ושיתוף הפעולה** (נשמר לעמודה `connection_cooperation`, המשותפת ל"התחברות ושיתוף פעולה" בטופס המלא באתר) - במכוון **לא** כל 14 השדות (משוב אמיתי מפורש: "לא צריך את כל הטופס... רק עד פרטים נוספים", כלומר עד לגבול שנקרא באתר "פרטים נוספים" - `LESSON_FIELDS_BASIC` ב-`public/app.html` - ועוד שדה אחד, שיתוף פעולה, שהתבקש בנפרד).

לכל שדה: קודם מנסים הכתבה חופשית בקול (Whisper, אותו מנגנון כמו שאר שדות הטקסט החופשי). **אם לא נשמע כלום** - לא ממשיכים לנסות שוב ושוב בקול (משוב אמיתי: "אם הוא מנסה ולא הולך") - מוצע גם להקיש 1 ולבחור מתוך עד 5 הניסוחים האחרונים מה"מילון" האישי (אותו `kind=lesson_<שדה>` בדיוק כמו באתר - ניסוח שהוכתב בטלפון מוצע גם באתר, ולהפך), נקראים ממוספרים ("1) ...", לא "1. ..." - נקודה נמחקת ע"י `sanitizeForYemot`) ונבחרים בהקשה בלבד. שאלת אישור אחת מרכזת בסוף את כל 4 השדות (מצב הקשה טהור - 1=אישור/2=שינוי חוזר לשדה הראשון/3=ביטול, ר' "תפריט הקטגוריות בטלפון" למעלה) - בכל מסלול (נשמר/בוטל) ממשיכים אחר כך להצעת דיווח המעקב הרגילה (`offerMentorNote`), בלי לשנות את הזרימה הקיימת שם.

## חונכות — בחירת תלמיד מתפריט ממוספר, לא רק בקול

משוב אמיתי ממשתמש: "אחרי שרשמתי כמה תלמידים... שיהיה לפי הרשימה, אם הראשון הוא X לחצו 1". בכניסה לקטגוריית "חונכות" (ימות בלבד) - אם לחונך כבר יש תלמידים רשומים, המערכת **לא** שואלת ישר "מה שם התלמיד?" (תלוי בזיהוי דיבור) - היא מקריאה תפריט ממוספר של עד 9 התלמידים שלו (מיון א-ב, כדי שהסדר יהיה עקבי בין שיחות): "על איזה תלמיד רוצים לדווח היום? 1) דנה כהן, 2) יוסי לוי... הקישו את המספר, או הקישו 0 אם התלמיד לא ברשימה." הקשת המספר עוברת ישר לבחירת סוג הפעולה, **בלי לומר את השם בקול בכלל**. הקשה **0** (או אמירת "אחר"/"שם אחר") היא שסתום-בטיחות למי שאין לו ברשימה (תלמיד חדש, או שיש יותר מ-9 ואינו בין הראשונים) - עוברת לשלב ההכתבה החופשית הרגילה (ר' "הוספה" למטה). אם בכל זאת הגיע קלט מדובר בשלב התפריט הממוספר (למשל בערוץ Twilio, שאין בו הקשות אמינות) - עדיין מנסים להתאים אותו לשם תלמיד קיים כרשת ביטחון, לפני שמוותרים. אם לחונך **אין** עדיין תלמידים רשומים בכלל, שום תפריט לא מוצג - שואלים ישר "מה שם התלמיד?" כרגיל (אין טעם בתפריט ריק).

## חונכות — הוספה/הסרה של תלמיד ישירות בטלפון, בלי לגשת לאתר

חונך יכול לנהל את רשימת התלמידים שלו גם מהטלפון, בלי לגשת לאתר בכלל:

- **הוספה**: בקטגוריית "חונכות", אם שם התלמיד שנאמר לא נמצא ברשימה **שלכם** (תלמיד נרשם תמיד תחת החונך שיצר אותו, `owner_user_id`), המערכת מציעה להוסיף אותו כתלמיד חדש על המקום ("רוצים להוסיף אותו כתלמיד חדש?") - אמירת "כן" (או הקשת 1 בימות) יוצרת את התלמיד ומיד ממשיכה לבחירת סוג הפעולה (כניסה/יציאה/מפגש רגיל), **באותה שיחה**.
- **הסרה**: אחרי בחירת תלמיד קיים, בנוסף לכניסה/יציאה/מפגש רגיל יש גם אפשרות "הסרת התלמיד" (הקשה 4 בימות) - למשל אם התלמיד כבר לא לומד עם החונך. זו **מחיקה רכה בלבד** (`students.active = 0`) - התלמיד רק מפסיק להופיע ברשימה הפעילה, אבל כל ההיסטוריה שלו (מפגשים, דוחות, הערות, מסמכים) נשארת שמורה במסד הנתונים ולא נמחקת. יש אישור לפני ביצוע בפועל ("אמרו כן לאישור"), כדי למנוע הסרה בטעות.
- אותה יכולת הסרה קיימת גם באתר: כפתור "הסרה" ליד כל תלמיד ברשימה (מסך "חונכות"), עם חלון אישור לפני ביצוע. הנתיב המשותף לשניהם: `DELETE /api/students/:id` (רק לבעלים של אותו תלמיד ספציפי).

## "בעל הקו" (admin) — מי מאשר גישה למפקחים, ואיך קובעים מי הוא

**מי זה "בעל הקו"? לא "המשתמש הראשון שנרשם"** (זה עלול להיות חשבון שנוצר אוטומטית מהטלפון, עם סיסמה אקראית שאיש לא בחר). "בעל הקו" הוא מי ש**תובע** את התפקיד בפועל, ורק אם הוא עומד בשני תנאים:
1. **נרשם באתר עצמו** (`signup_channel='web'`) - כלומר מילא טופס הרשמה ובחר סיסמה בעצמו, לא חשבון שנוצר אוטומטית מהטלפון (`signup_channel='phone'`, ר' "הרשמה ישירות בטלפון" למעלה) - חשבונות כאלה חסומים מהתביעה הזו, גם אם יש להם טלפון וסיסמה.
2. **מאמת בפועל** שהוא הבעלים של הטלפון/המייל הרשום שלו, דרך קוד אישור בן 4 ספרות שנשלח אליו בערוץ שיבחר - **שיחה קולית** או **מייל** (אותו מנגנון בדיוק כמו שחזור סיסמה).

**איך תובעים את התפקיד** (במסך "הגדרות" באתר, כרטיס "בעל/ת הקו" - מוצג רק אם עדיין אין בעל קו במערכת, ואתם כשירים):
1. `GET /api/me/admin-claim-status` - בודק אם כבר יש בעל קו, ואם אתם כשירים (רשומים באתר + יש טלפון או מייל בפרופיל).
2. `POST /api/me/request-admin-claim` עם `channel: "phone"` (ברירת מחדל) או `channel: "email"` - שולח קוד בן 4 ספרות לערוץ שנבחר, **שלכם עצמכם** (זה אימות עצמי - לא כמו אישור מפקח למטה שדורש שני אנשים). ערוץ המייל נוסף כדי שאפשר יהיה לתבוע את התפקיד באמת (לא רק במצב בדיקה) ברגע שהוגדר SendGrid, גם בלי לשלם על Twilio לערוץ הטלפון.
3. `POST /api/me/confirm-admin-claim` עם הקוד - אם נכון ולא פג תוקף (10 דקות), ואם עדיין אין בעל קו אחר (מגן מפני מירוץ), התפקיד מתווסף.

ברגע שיש בעל קו אחד, אף אחד אחר לא יכול לתבוע את התפקיד (409) - אין דרך "לגנוב" את זה מאוחר יותר.

## תפקיד "מפקח" — דורש אישור בעל הקו, לא הצהרה עצמית

תפקיד `supervisor` (מפקח/ת) שונה משאר התפקידים המקצועיים (`mentor`/`therapist`): הוא נותן גישה לצ'אט הפנימי ולדוחות של **כל** תלמיד במערכת, לא רק תלמידים שרשמתם בעצמכם - ולכן אי אפשר להצהיר עליו לבד דרך הרשמה או עדכון פרופיל (השדה `roles` מסנן אותו אוטומטית בשני המקומות האלה). רק ל-`admin` (בעל הקו, ר' למעלה) יש סמכות לאשר בקשות למפקח.

**איך זה עובד בפועל** (במסך "הגדרות" באתר, כרטיס "הרשאת מפקח/ת"):
1. מי שרוצה להיות מפקח מזין את **מספר הטלפון של בעל הקו** (`POST /api/me/request-supervisor`).
2. אם המספר נכון - נשלח קוד אישור בן 4 ספרות **למייל הרשום של בעל הקו** (לא למבקש!). התשובה מה-API זהה גם אם המספר שגוי, כדי לא לחשוף מי בעל הקו בניחוש.
3. בעל הקו (שרואה את הקוד במייל שלו) מעביר אותו בעל-פה/בטלפון למי שביקש.
4. המבקש מזין את הקוד (`POST /api/me/confirm-supervisor`) - ואם הוא נכון ולא פג תוקף (10 דקות), התפקיד מתווסף בפועל.

השליחה בפועל של שני קודי האישור האלה (`src/services/recoveryChannel.js`, אותו שירות ששולח קודי שחזור סיסמה) פועלת במצב MOCK כרגע - הקוד גם מוחזר בתשובת ה-API (`demoCode`) לצורך בדיקה. **חשוב, ובמיוחד כאן**: קוד אישור מפקח תמיד נשלח למייל (לא לשיחה קולית) - כל עוד `EMAIL_MOCK=true` (ברירת המחדל), הקוד "מגיע" בפועל ישירות לתשובת ה-API (ומוצג במסך של **המבקש עצמו**, לא רק של בעל הקו) - כלומר **כל עוד לא מוגדר מייל אמיתי, כל אחד יכול להעניק לעצמו הרשאת מפקח בלי אישור אמיתי של בעל הקו**. ר' "מייל אמיתי בחינם" למטה - זו הסיבה המרכזית שכדאי להפעיל את זה מוקדם, גם בלי לגעת בכלל בשיחות קוליות (Twilio, שעולות כסף).

## מייל אמיתי בחינם (SendGrid) - סוגר את פרצת קוד המפקח, בלי לשלם על שיחות קוליות

**תוקן (בעקבות בקשת פיצ'ר - "תמצא לי משהו חינמי לגמרי")**: שליחת מייל אמיתי (בניגוד לשיחות קוליות) אפשרית **בחינם לגמרי** דרך SendGrid, בתוכנית החינם שלהם (עד 100 מיילים ביום - מעבר בהרבה לצורך כאן). זה משודרג/ה-mock **בנפרד לגמרי** משיחות קוליות (`RECOVERY_MOCK`, שנשאר במצב בדיקה עד שתרצו לשלם על Twilio) - אפשר להפעיל מייל אמיתי היום, ולהשאיר שיחות קוליות במצב בדיקה כרגע.

**מה זה משפר בפועל, מיד**: (1) מיילים אמיתיים להורים על דוחות התקדמות חדשים (כבר קיים בקוד, היה רק ב-MOCK). (2) **סוגר את פרצת האבטחה שתוארה למעלה** - קוד אישור מפקח יגיע רק לתיבת המייל האמיתית של בעל הקו, לא יוצג יותר למי שמבקש. (3) שחזור סיסמה בערוץ "מייל" (ר' מסך הכניסה, "שכחתי סיסמה") יהפוך לאמיתי - שיחה קולית תישאר עדיין במצב בדיקה.

**שלבי הרשמה** (חד-פעמי, כ-10 דקות, בלי כרטיס אשראי):
1. נרשמים בכתובת [signup.sendgrid.com](https://signup.sendgrid.com) (חשבון חינמי - Free Plan).
2. מאמתים את כתובת המייל שנרשמתם איתה (מייל אישור שיישלח אליכם).
3. **חובה**: מאמתים "Single Sender" - בלוח הבקרה של SendGrid, Settings → Sender Authentication → Verify a Single Sender. ממלאים טופס עם כתובת מייל שאתם מחזיקים בה בפועל (למשל הג'ימייל שלכם, או `no-reply@` בדומיין שלכם אם יש) - זו הכתובת שממנה יישלחו כל המיילים. מגיע מייל אישור לכתובת הזו - לוחצים על הקישור שבו.
4. יוצרים מפתח API: Settings → API Keys → Create API Key. נותנים לו שם (למשל "hapinkas-sheli"), הרשאות "Full Access" מספיקות (או "Restricted Access" עם "Mail Send" בלבד, אם רוצים לצמצם). מעתיקים את הערך (מתחיל ב-`SG.`) - **מוצג פעם אחת בלבד**, לשמור במקום בטוח.
5. בלוח הבקרה של Render, בשירות שלכם → **Environment** → מוסיפים שני משתני סביבה:
   - `EMAIL_MOCK` עם הערך `false`
   - `SENDGRID_API_KEY` עם המפתח שהעתקתם בשלב 4
   - `EMAIL_FROM` עם הכתובת המדויקת שאימתתם בשלב 3 (Single Sender) - **חייבת להיות זהה**, אחרת SendGrid ידחה את השליחה.
6. שומרים - Render יפרוס מחדש אוטומטית. אין צורך לגעת ב-`RECOVERY_MOCK`/`TWILIO_MOCK` בכלל.

**איך בודקים שזה עבד**: בהגדרות באתר → "הרשאת מפקח/ת" → מבקשים בקשה (עם מספר הטלפון של בעל הקו) - הפעם לא אמור להופיע קוד על המסך בכלל (התיבה הצהובה של "מצב בדיקה" לא תופיע) - בעל הקו אמור לקבל את הקוד בתיבת המייל האמיתית שלו תוך שניות.

## שיחת אימות טלפונית חינמית דרך ימות המשיח — נוסה ונכשל, אין כרגע דרך חינמית לטלפון

**נוסה (בעקבות בקשת פיצ'ר) ובוטל אחרי בדיקה חיה (2026-08-18)**: הייתה פה תכונה שניסתה להשתמש ב-API של ימות המשיח בשם `DoubleAuth` כדי לשלוח "שיחת אימות" חינמית (שיחה שלא עונים לה, 4 הספרות האחרונות של המספר המתקשר הן הקוד) לכל מספר טלפון של משתמש באפליקציה - בלי Twilio ובלי עלות נוספת.

**מה קרה בבדיקה**: השיחה נכשלה עם השגיאה `unable to authenticate in AUTH_TOKEN session`. בדיקה נוספת בתיעוד הציבורי (פורום מפתחי ימות) גילתה שה-API הזה **לא מיועד למה שחשבנו**: הוא משמש לאבטחת ההתחברות (Login) של בעל החשבון עצמו ל-API של ימות (session שנוצר עם שם משתמש+סיסמה), ולא כשירות כללי לשליחת שיחת-אימות לכל מספר טלפון שנבחר (כמו Twilio Verify). במילים אחרות - זו תכונת אבטחה פנימית של ימות למפתחים שמתחברים ל-API שלהם, לא כלי ששלום יכול לגייס כדי לאמת את הטלפון של מפקח/מתשחזר-סיסמה.

**המסקנה המעשית**: **אין כרגע דרך חינמית** לשלוח שיחת-אימות אמיתית לטלפון של משתמש קצה. שלוש האפשרויות שנשארות:
1. **מייל אמיתי בחינם** דרך SendGrid (הסעיף למעלה) - כבר עובד, ומכסה את פרצת האבטחה למי שיש לו כתובת מייל רשומה.
2. **שיחה טלפונית אמיתית בתשלום** דרך Twilio (ר' README, המחירים שנבדקו בעבר) - אם רוצים גם ערוץ טלפוני אמיתי.
3. **המשך עבודה במצב בדיקה** (`RECOVERY_MOCK`, ברירת המחדל) לערוץ הטלפוני - הקוד מוצג במסך בתיבה הצהובה, תקין לבדיקות/פיתוח, לא מומלץ בתור ההגנה היחידה בפרודקשן בלי גם מייל אמיתי מוגדר.

הקוד של הניסיון (`services/yemotAuth.js`) נשאר בפרויקט לתיעוד, אבל **אינו נקרא יותר** משום מקום - `services/recoveryChannel.js` חזר להתנהגות הקודמת (בדיקה/Twilio בלבד לערוץ הטלפוני).

## "מנהל מערכת" — כפתור ישיר להענקת/הסרת מפקח, מוגן בסיסמה מיוחדת (לא תלוי בתהליך הקוד למעלה)

**תוקן (בעקבות בקשת פיצ'ר)**: התהליך הקיים לתפקיד מפקח (למעלה) דורש שני אנשים - מי שרוצה להיות מפקח יוזם בקשה, בעל הקו מקבל קוד למייל שלו ומעביר אותו בעל-פה. במקרה שבו יש בעל קו יחיד שהוא גם בפועל מנהל את כל המערכת, זה מרגיש עקיף מדי. נוסף **ערוץ נוסף ומהיר יותר** - "מנהל מערכת" - שמאפשר להעניק (או להסיר) הרשאת מפקח למשתמש כלשהו ישירות, בלי שהוא צריך ליזום כלום ובלי קוד. **זה לא מחליף** את התהליך הקיים דרך בעל הקו - שני הערוצים פעילים במקביל.

**איך זה עובד**:
1. **שלב חד-פעמי בצד השרת**: ב-Render, Environment, מוסיפים משתנה סביבה חדש בשם `SYSTEM_ADMIN_PASSWORD` עם סיסמה ארוכה וייחודית שאתם בוחרים (**לא** סיסמת ההתחברות הרגילה שלכם לאתר, ולא סיסמה שכבר בשימוש במקום אחר). **כל עוד המשתנה הזה לא מוגדר, כל תכונת "מנהל מערכת" כבויה לגמרי** - אין שום דרך לגשת אליה, בדיוק כמו שאר התכונות האופציונליות במערכת (Whisper/Twilio/Cardcom).
2. באתר, במסך "הגדרות", יש כרטיס חדש בשם **"מנהל מערכת"** - מזינים שם את הסיסמה שבחרתם, ואת שם/שם משתמש/טלפון של האדם שרוצים להפוך למפקח (או להסיר ממנו את ההרשאה), לוחצים "חיפוש", ואז יש כפתור "הפוך למפקח/ת" (או "הסרת הרשאת מפקח") ליד השורה שלו ברשימת התוצאות.
3. הפעולה מתבצעת מיד - אין קוד, אין המתנה לאישור צד שני.

**חשוב לדעת**: הכרטיס הזה מוצג לכל מי שנכנס למסך ההגדרות (בדיוק כמו כרטיס "בעל/ת הקו" הרגיל) - ההגנה היחידה היא הסיסמה עצמה. מי שמחזיק בסיסמה יכול להעניק/להסיר הרשאת מפקח לכל משתמש במערכת, בלי שום אימות נוסף - לכן חשוב לבחור סיסמה ארוכה וייחודית, ולשתף אותה רק עם מי שבאמת אמור להיות "מנהל מערכת" (למשל: אתם עצמכם בלבד).

## מסמכים - העלאת קבצים לתיק תלמיד

`POST /api/students/:id/documents` מאפשר להעלות קובץ (למשל את הטופס הסרוק/המקורי, או כל מסמך אחר) לתיק תלמיד. הראוט שלנו (`router.js`) תומך רק בגוף JSON (אין תלות ב-multipart/form-data חיצוני), אז ההעלאה מתבצעת כ-base64: הדפדפן קורא את הקובץ עם `FileReader.readAsDataURL` ושולח `{ title, filename, mime_type, data_base64 }`. הקובץ עצמו נשמר בדיסק (`backend/data/uploads/<student_id>/...`, ניתן לשינוי מיקום דרך `UPLOADS_DIR`), וב-DB (`documents`) נשמרת רק המטא-דאטה. **ברשימה (`GET /api/students/:id/documents`) מוצגות רק כותרות** - לצפייה בתוכן המלא יש נתיב הורדה נפרד (`GET /api/documents/:id/download`). הגבלת גודל: 15MB לקובץ. הרשאה כמו `/file` - בעלים/חונך/מטפל/מפקח בלבד, **לא** הורים (נחשב תוכן פנימי/מנהלתי).

## ייבוא תנועות מאקסל/CSV/PDF - דפי בנק וכרטיס אשראי

בקשת פיצ'ר ממשתמש: "רוצה להכניס אקסל של דפי בנק או דפי כרטיס אשראי, שיוכל להוריד אותו והמערכת תכניס את זה להכנסות והוצאות" (ובהמשך, אחרי ששלח קובץ Excel אמיתי: "PDF תוכל גם לפענח?"). מוגש בעמוד "תנועות" באתר, כרטיס "ייבוא תנועות מאקסל / CSV".

**זרימה בשני שלבים בכוונה** (בדיוק כמו יבוא כספי בכל מערכת רצינית) - **אף פעם לא שומרים תנועות ישירות מקובץ בלי שהמשתמש ראה ואישר אותן**, כי טעות בזיהוי עמודה יכולה ליצור בבת אחת הרבה תנועות שגויות:
1. `POST /api/transactions/import/parse` - מפרק את הקובץ, מזהה עמודות ומחזיר תצוגה מקדימה. **לא נוגע במסד הנתונים בכלל.**
2. תצוגה מקדימה בטבלה: לכל שורה - תיבת סימון (מסומנת כברירת מחדל, חוץ משורות שכבר יובאו בעבר - ר' למטה), תאריך/תיאור/סכום (לקריאה בלבד), וסוג/קטגוריה **ניתנים לעריכה** לפני השמירה (כולל כפתור "החל על כל השורות המסומנות" לקטגוריה אחידה).
3. `POST /api/transactions/import/commit` - שומר רק את השורות שסומנו, עם `source='import'`.

**קלט נתמך**: קובצי `.xlsx` (Excel אמיתי), `.csv`, `.pdf`, וגם **"אקסל" שהוא בפועל טבלת HTML** עם סיומת `.xls`/`.xlsx` (טריק ותיק ונפוץ **מאוד** אצל בנקים/חברות אשראי בישראל - Excel פותח קובץ כזה בלי בעיה כי הוא מזהה תוכן לפי החתימה בפועל, לא לפי הסיומת). זיהוי הפורמט הוא **לפי תוכן הקובץ בפועל**, לא לפי הסיומת - כי הסיומת לבדה לא אמינה (נבדק וווידא מול קובץ ייצוא אמיתי מבנק מרכנתיל-דיסקונט, `AccountActivity.xls`, שהתברר בדיוק כזה). בלי שום ספרייה חיצונית (ר' "למה אפס תלויות" למעלה) - ארבעה פרסרים עצמאיים:
- `src/lib/xlsxParser.js` - קובץ `.xlsx` אמיתי הוא בעצם ארכיון ZIP רגיל שמכיל כמה קבצי XML. מפרקים את ה-ZIP ביד (End Of Central Directory → תיקייה מרכזית → קבצים, עם `zlib.inflateRawSync` המובנה של Node לדחיסת DEFLATE), ומפרקים את ה-XML הרלוונטי (`sharedStrings.xml`, `styles.xml`, גיליון העבודה) בביטויים רגולריים - מספיק לקבצים השטוחים והפשוטים האלה, בלי צורך בפרסר DOM מלא. גם ממיר מספרים סידוריים של תאריכי אקסל (ימים מאז 1899-12-30) ל-ISO, לפי זיהוי איזה תאים מעוצבים בפועל כתאריך (`numFmtId` ב-`styles.xml`).
- `src/lib/htmlTableParser.js` - מזהה קובץ שמתחיל (אחרי BOM אם יש) ב-`<html`/`<table` במקום בחתימת ZIP ("PK"), ומפרק את תגיות `<tr>`/`<td>` בביטויים רגולריים לאותה מטריצת-שורות בדיוק כמו שאר הפרסרים - כך ש-`importMapping.js` לא צריך לדעת בכלל מאיזה פורמט הגיעו השורות. קובץ `.xls` **ישן-אמיתי** (בינארי, פורמט Excel 97-2003/OLE) מזוהה בנפרד לפי חתימת הבתים שלו (`D0 CF 11 E0 A1 B1 1A E1`) ומחזיר הודעת שגיאה ברורה שמנחה לשמור מחדש כ-xlsx/csv - **לא נתמך** (פורמט בינארי סגור לגמרי, לא קשור ל-ZIP/XML/HTML).
- `src/lib/csvParser.js` - פרסר CSV שתומך בשדות מצוטטים ומזהה אוטומטית את המפריד (פסיק/נקודה-פסיק/טאב - חלק מהבנקים בישראל מייצאים עם נקודה-פסיק).
- `src/lib/pdfParser.js` - **הפרסר המורכב מכולם**, נבנה בעקבות "PDF תוכל גם לפענח?" ונבדק מול קובץ אמיתי (דף פירוט דיגיטלי של כאל). PDF, בניגוד ל-xlsx/CSV/HTML, אין בו בכלל מושג מובנה של "טבלה" - יש רק טקסט ממוקם בקואורדינטות (x,y) על העמוד, וצריך לשחזר את מבנה הטבלה מהמיקומים:
  1. פענוח מבנה האובייקטים של ה-PDF (סריקת "N 0 obj...endobj" ישירות - עמיד גם אם טבלת ה-xref הפורמלית פגומה מעט), כולל פענוח זרמי FlateDecode (`zlib.inflateSync`).
  2. איתור גופן העמוד ופענוח מפת ה-`ToUnicode` שלו (טבלת קוד-תו → יוניקוד אמיתי - בלי זה הטקסט המחולץ הוא ג'יבריש).
  3. הרצת אופרטורי זרם התוכן (`BT`/`Td`/`Tm`/`Tj`/`TJ`) כדי לקבל רשימת "ריצות טקסט" עם קואורדינטת מיקום לכל אחת.
  4. קיבוץ ריצות לשורות (לפי `y` דומה) ולעמודות (לפי קרבת `x` למרכז עמודת הכותרת המתאימה - נגזר משורת הכותרות שזוהתה, בדיוק כמו זיהוי העמודות בפורמטים האחרים, רק לפי מיקום ולא לפי אינדקס עמודה).
  5. **תיקון כיווניות (bidi)**: התגלה מול הקובץ האמיתי שה-PDF מצייר כל תו בעברית *ובמספרים* כריצת-טקסט נפרדת, ממוקמות מימין לשמאל לפי סדר תצוגה חזותי - כלומר תאריך כמו "19/07/2026" מגיע כ-10 ריצות-תו בודדות בסדר "הפוך" (`reorderRunsForReading` מתקן את זה - הופך רק "מקטעים" רציפים שאינם עברית, כי טקסט עברי כבר מגיע נכון).
  קובץ PDF מוצפן, או PDF בלי טקסט הניתן לחילוץ (למשל מסמך סרוק/תמונה - אין בו `ToUnicode` בכלל), מזוהים בנפרד ומחזירים הודעת שגיאה עברית ברורה במקום ניסיון פענוח שגוי.

**זיהוי עמודות אוטומטי** (`src/lib/importMapping.js`) - **בלי לדעת מראש** איזה בנק/חברת אשראי זה, כי כל גוף מייצא כותרות עמודות שונות לגמרי: סורקים את 15 השורות הראשונות ומחפשים את זו עם הכי הרבה התאמות למילות-מפתח מוכרות (עברית ואנגלית) - "תאריך"/date, "תיאור"/"פרטים"/description, "זכות"/credit, "חובה"/"חיוב"/debit, "סכום"/amount, "יתרה"/balance. שני מקורות סוג נתמכים, עם היגיון ברירת-מחדל שונה לכל אחד (**ניתן לשנות ידנית כל שורה בתצוגה המקדימה**, זו רק ברירת מחדל):
- **דף בנק** (`source_type: "bank"`): אם יש עמודות "זכות"/"חובה" נפרדות - נגזר ישירות מהן (זכות>0 → הכנסה, חובה>0 → הוצאה). אם יש רק עמודת סכום אחת - סכום שלילי נחשב הוצאה, חיובי הכנסה.
- **דף כרטיס אשראי** (`source_type: "card"`): לרוב עמודת סכום יחידה בלבד. ברירת המחדל הפוכה מבנק - סכום חיובי (רוב השורות, חיובים רגילים) → הוצאה, סכום שלילי (זיכוי/החזר) → הכנסה.

**תיאור חלופי כשעמודת "פרטים" ריקה** (נתגלה מול קובץ Excel אמיתי - מזרחי טפחות): בחלק מהבנקים עמודת "פרטים" (התיאור המדויק ביותר, למשל "לטובת: ...") מלאה רק בחלק מהשורות (למשל, ריקה בהוראות קבע ועמלות) - שם עמודת "הפעולה" (למשל "הו\"ק הלו' רבית", "זיכוי מהמזרחי") היא בפועל התיאור השימושי היחיד. `HEADER_KEYWORDS.descriptionFallback` מזהה עמודת גיבוי כזו בנפרד (לא ברשימת התיאור הראשית - אחרת "הפעולה" הייתה "מנצחת" את "פרטים" המדויקת יותר לפי סדר עמודות), ו-`rowsToTransactions` נופלת אליה **רק לשורה ספציפית** שבה "פרטים" ריקה - לא מחליפה גורף.

**תיאור מורחב, בכיוון עדיפות הפוך** (נתגלה מול קובץ Excel אמיתי - בנק לאומי): שם התמונה הפוכה - עמודת "תיאור" **כמעט אף פעם לא ריקה**, אבל לרוב גנרית וחסרת תוכן ("כרטיס דביט" לעשרות שורות שונות לגמרי), בעוד עמודת "תאור מורחב" (למשל "מתאריך 20/08/26 23:42 בכרטיס המסתיים ב-4847 ב-פלומה") מכילה את הפרטים השימושיים באמת - אבל היא זו שלפעמים ריקה. `HEADER_KEYWORDS.descriptionExtended` (`descExtendedCol`) עדיפה **בכל פעם שהיא מלאה**, לא רק כשהראשית ריקה - כיוון עדיפות הפוך במפורש מ-`descriptionFallback` (נבדק בפועל: מתוך 51 תנועות בקובץ האמיתי, 42 קיבלו תיאור מפורט במקום "כרטיס דביט" הגנרי).

**עמודות סכום/יתרה בלי כותרת טקסט בכלל** (נתגלה מול קובץ Excel אמיתי - ייצוא "עובר ושב"): חלק מהבנקים משאירים את כותרות עמודות הסכום/היתרה **ריקות לגמרי** - העמודות עצמן קיימות עם מספרים אמיתיים לכל שורה, פשוט בלי טקסט כותרת (כנראה מסתמכים על מיקום/עיצוב ולא על טקסט). `guessUnlabeledAmountColumn` (`src/lib/importMapping.js`) היא רשת ביטחון שמופעלת רק אם זיהוי לפי מילות-מפתח נכשל לגמרי: סורקת כמה שורות נתונים ומחפשת את העמודה המספרית הראשונה (לפי סדר אינדקס) שעדיין לא "תפוסה" ע"י עמודת תאריך/תיאור שכבר זוהו. **תוקן תוך כדי**: מחרוזת תאריך כמו "2026-08-21" "מצליחה" להיקרא כמספר (2026) לפי `parseAmountValue` - בלי בדיקה מפורשת שהעמודה לא נראית כמו תאריך (`normalizeDateValue`), עמודת "תאריך ערך" נוספת (לא רק עמודת התאריך הרשמית) הייתה מזוהה בטעות כעמודת הסכום.

**עדיפות "סכום חיוב" על "סכום עסקה"** (נתגלה מול קובץ PDF אמיתי של כאל): דפי כרטיס אשראי מפרטים בדרך כלל **שתי** עמודות סכום - "סכום עסקה" (הסכום המקורי, יכול לכלול תשלומים עתידיים/המרת מטבע) ו"סכום חיוב" (מה שבפועל מחויב בחודש הנוכחי). `findColumnPreferred` (`src/lib/importMapping.js`) בוחרת במפורש בעמודת ה"חיוב" כשקיימות שתיהן - זה הסכום הרלוונטי למעקב תקציב שוטף. באותו הקשר: מסלול "זכות/חובה" (עמודות עו"ש נפרדות) דורש עכשיו ששתי העמודות יימצאו **יחד** כדי להיבחר - כי המילה "חיוב" מופיעה גם ברשימת מילות המפתח של "חובה", ובלי הדרישה הזו עמודת "סכום חיוב" בכרטיס אשראי הייתה מתפרשת בטעות כעמודת "חובה" בודדת.

**מניעת כפילויות בין ייבוא לייבוא**: לכל תנועה מיובאת מחושבת טביעת-אצבע (hash של משתמש+תאריך+סכום+סוג+תיאור, ר' `import_hash` בטבלת `transactions` + אינדקס ייחודי חלקי ב-`db.js`) - כך שאפשר להעלות את אותו קובץ (או קובץ חופף, למשל דף חדש שמכיל גם כמה עסקאות שכבר הופיעו בדף הקודם) כמה פעמים בלי ליצור תנועות כפולות. בתצוגה המקדימה, שורות שכבר יובאו בעבר מסומנות ("כבר יובא") ולא מסומנות אוטומטית לייבוא חוזר - אבל אפשר עדיין לסמן אותן ידנית אם צריך.

**מגבלות ידועות**: בנק/חברת כרטיס אחר עם פורמט ייצוא חריג עוד יותר (למשל כותרות בשפה שלישית, או שם עמודת תיאור/סכום יוצא-דופן נוסף) עלול עדיין לא להיזוהות אוטומטית - במקרה כזה מוצגת הודעת שגיאה ברורה ("לא זוהתה שורת כותרות מוכרת") במקום ניסיון ייבוא שגוי בשקט. אם זה קורה בפועל מול קובץ אמיתי, הפתרון הוא הרחבת רשימות מילות-המפתח ב-`HEADER_KEYWORDS` (`src/lib/importMapping.js`) לפי הכותרות המדויקות שהתגלו - בדיוק כמו שכבר נעשה כמה פעמים. ספציפית ל-PDF: שדה "תיאור" (שם בית עסק) לפעמים נחתך/מתמזג עם שדה סמוך אם הטקסט רחב מדי לעמודה שלו (לא משפיע על דיוק התאריך/סכום - רק קוסמטי), ורק כתובי-CID עם `ToUnicode` נתמכים (רוב המפיקים המודרניים, אבל לא כולם) - PDF סרוק (תמונה בלבד, בלי טקסט) לא נתמך כלל ומחזיר שגיאה ברורה.

**עדכון (קובץ אמיתי נוסף - מזרחי טפחות, PDF עו"ש "tnuot.pdf"): טקסט בתוך Form XObject מקונן + עמודת סכום משולבת.** המשתמש שלח PDF אמיתי שנכשל לגמרי ("לא נמצאו עמודות תקינות") - התבררו שלוש בעיות אמיתיות ביחד, כולן תוקנו ב-`pdfParser.js`/`importMapping.js`:
1. **הטקסט לא מצויר ישירות בזרם התוכן של העמוד.** זרם התוכן של העמוד רק קובע חיתוך+טרנספורמציה (`cm`) ו"מזמין" Form XObject מקונן (`/Name Do`) שבו נמצא כל הטקסט בפועל (129 קריאות `Tj`, בשני גופנים נפרדים דרך `Tf`). נוסף מנוע מעקב מטריצות CTM מלא (`q`/`cm`/`Q`, כפל מטריצות 2D) ופתרון `Do` רקורסיבי (`walkContentStream`, עד 8 רמות קינון, כולל דילוג על XObjects שהם תמונות) - בלי זה כל הטקסט "נעלם" (0 ריצות).
2. **כיווניות שונה מקובץ כאל.** בקובץ כאל כל תו עברי הוא ריצת-`Tj` נפרדת (ריצות כבר בסדר קריאה נכון, רק *סדר הריצות* של רצפים לא-עבריים היה הפוך). כאן, לעומת זאת, כל *ביטוי* עברי שלם (מילה/צירוף מילים) הוא ריצה אחת, אבל *הפוכה-פנימית* (למשל "תידוהיו םולש גרבנייטש" במקום "שטיינברג שלום ויהודית") - תואם בדיוק לדרישת התקן של PDF לשמור טקסט RTL ב"סדר תצוגה" ולא ב"סדר לוגי". `reorderRunsForReading` הופך עכשיו גם ריצה עברית *בתוך עצמה* (כולל מיפוי סוגריים - "(" הופך ל-")" ולא נשאר "(") - עבור ריצה בת-תו-אחד (כאל) זה no-op, אז זה לא שבר את התיקון הקודם.
3. **עמודת סכום "זכות/חובה" משולבת, לא שתי עמודות נפרדות.** מילות המפתח "זכות" ו"חובה" שתיהן תואמות לאותה כותרת ממוזגת, כך ש-`creditCol`/`debitCol` הצביעו על *אותה* עמודה - ערך שלילי (הוצאה) לא עבר אף אחד משני התנאים ונעלם בשקט. `rowsToTransactions` מבטלת עכשיו זיהוי זכות/חובה כשהן מצביעות על אותה עמודה בדיוק, ונופלת ל-`guessUnlabeledAmountColumn` (לפי סימן).

בנוסף תוקנו שני באגים נלווים שהתגלו תוך כדי: שורת "יתרה קודמת נכון ל-..." (שורת סיכום, לא המשך-כותרת) הייתה נתפסת בטעות כשורת המשך-כותרת דו-שורתית (הבדיקה עכשיו: המשך-כותרת אמיתי לא מכיל *אף* ספרה באף ריצה שבו, לא רק בריצה הימנית); ושמות משאבים (גופנים/XObjects) עם "+"/"-" (נפוץ בשמות גופן-משנה מוטמע) נקטעו ע"י הביטוי הרגולרי הישן לזיהוי Name. נבדק מקצה לקצה מול הקובץ האמיתי: **75/75 תנועות זוהו נכון**, כולל התאמה מדויקת (עד אגורה) מול חישוב יתרה עצמאי מהיתרה הקודמת שצוינה בקובץ.

### מחיקת קובץ ייבוא שלם בבת אחת

משוב אמיתי: "אני צריך אופציה שנוכל למחוק נתונים שהבאתי בהכנסות... אם הבאתי דפי בנק ואני רוצה למחוק את הקבצים שהועלו, שיהיה אופציה לבחור למחוק מהמערכת". עד כה אפשר היה למחוק רק תנועה-תנועה (`DELETE /api/transactions/:id`) - לא מעשי לקובץ עם עשרות שורות.

כל התנועות שנשמרות יחד מקריאת `commit` אחת (כלומר מהעלאת קובץ אחת) מקבלות `import_batch_id` (UUID) + `import_filename` משותפים (`db.js`, `importTransactions.js`). כרטיס "ייבוא תנועות" באתר מציג רשימת "קבצים שיובאו" (`GET /api/transactions/import/batches` - קיבוץ לפי `import_batch_id` עם שם קובץ/מספר תנועות/טווח תאריכים/סכומים) וכפתור "מחיקת הקובץ" לכל אחד (`DELETE /api/transactions/import/batches/:batchId` - מוחק בבת אחת את כל התנועות של אותה אצווה, ownership-checked).

## תקציב חתונה - אזור נפרד לגמרי

משוב אמיתי: "שיהיה קטגוריה נפרדת להוצאות חתונה, הכנסות מתרומות... תחת קטגוריה של הוצאות יהיו לבחור ביגוד, אולם חתונה, שבע ברכות (לבחירה ימים - שבע ברכות יש 6 ימים, שבת - שבת ברכות), קייטרינג, מוזיקה, שמלת כלה, אירוסין, מתנות, אביזרים לדירה, ביגוד לילדים... כמו כן שאוכל לערוך ולשנות למחוק". לשאלה הבהרה - המשתמש אישר שמדובר באזור/מסך נפרד לגמרי מ"תנועות" (לא עוד קטגוריות בתוך התקציב הרגיל), ו"לערוך ולשנות" מתייחס לעריכת תנועה שכבר הוזנה (לא רק מחיקה).

**מימוש**: טבלה נפרדת לגמרי (`wedding_transactions`, `db.js`) ונתיב API נפרד (`src/routes/weddingTransactions.js`) - לא נוגע כלל ב-`transactions` הרגילה, ולכן לא משפיע על חישוב המעשרות/היתרה הרגילים. מסך "חתונה" חדש בתפריט הצד (`public/app.html`) עם:
- **הכנסה**: קטגוריה קבועה "תרומות" (+ "אחר" חופשי).
- **הוצאה**: רשימת קטגוריות קבועה ל-`<select>` (לא טקסט חופשי, כי המשתמש פירט רשימה מדויקת): ביגוד, אולם חתונה, שבע ברכות - יום 1 עד יום 6 (6 קטגוריות נפרדות, אחת לכל יום), שבת ברכות (קטגוריה נפרדת משבע-הברכות הרגילות), קייטרינג, מוזיקה, שמלת כלה, אירוסין, מתנות, אביזרים לדירה, ביגוד לילדים, ועוד "אחר" חופשי (נשמר למילון נפרד - `wedding_expense_category_other`/`wedding_income_category_other` - לא מתערבב עם מילון הקטגוריות של התנועות הרגילות).
- **עריכה בפועל** (`PUT /api/wedding/transactions/:id`) - לא רק מחיקה: לחיצה על "עריכה" בשורת תנועה הופכת אותה לטופס inline (סוג/קטגוריה/סכום/הערה) עם "שמירה"/"ביטול", בלי לצאת מהרשימה. זו התכונה היחידה מהסוג הזה במערכת כרגע - בתנועות הרגילות ובשאר המקומות אפשר עדיין רק למחוק ולהוסיף מחדש.
- כרטיס "הוצאות לפי קטגוריה" (עיגול/donut, בדיוק אותו רכיב SVG כמו בעמוד "תנועות" הרגיל - `renderCategoryDonut` הוכלל לקבל אלמנט-יעד כפרמטר).

## תקציב דירה - עוד אזור נפרד לגמרי (כמו חתונה)

משוב אמיתי (המשך ישיר לבקשת "חתונה" למעלה): "כמו שיש הוצאות והכנסות יש גם חתונה... אני צריך שיהיה שני קטגוריות נפרדות: 1 חתונה, 2 דירה. בתוך דירה יש שני אפשרויות רגיל, תבע משותף" - ותחת "תבע משותף" פירט את תת-העלויות: עלות בנייה, עלות עו"ד/הסכם, עלות יועץ משכנתאות, עלות מיסים.

**מימוש**: אותו דגם בדיוק כמו "חתונה" (טבלה נפרדת `apartment_transactions`, נתיב API נפרד `src/routes/apartmentTransactions.js`, מסך "דירה" נפרד בתפריט) - לא נוגע בכלל לא בתנועות הרגילות ולא בחתונה, שלושה אזורים נפרדים לגמרי. קטגוריות הוצאה קבועות: "רגיל" (פריט שטוח יחיד) + ארבע תת-עלויות של "תבע משותף" (כל אחת פריט נפרד ב-`<select>`, בדיוק כמו פירוק "שבע ברכות" ליום-ביום בחתונה) + "אחר" חופשי. הכנסה: רק "אחר" חופשי כרגע - לא צוינו קטגוריות הכנסה קבועות ל"דירה" (בניגוד ל"תרומות" בחתונה).

לא בוצע כרגע איחוד קוד בין "חתונה" ל"דירה" (שני קבצים כמעט זהים, נשמרים מפורשים ונפרדים בכוונה, תואם לסגנון הקוד הקיים - למשל ארבעת פרסרי הייבוא הנפרדים) - אם יתווסף אזור נפרד שלישי כזה בעתיד, זה יהיה הרגע הנכון לשקול מודול משותף גנרי במקום עוד העתקה.

### "בחר הכל" למחיקה מרובה - בתנועות, בחתונה, ובדירה

משוב אמיתי: "במחיקות של התנועות שיהיה סמן הכל כדי שאני לא יצטרך למחוק 1 1 1". תיבת סימון לכל שורה + תיבת "בחר הכל" מעל הרשימה + כפתור "מחיקת המסומנות" - בשלוש רשימות התנועות (רגילות, חתונה, דירה). מימוש **פרונט-בלבד** (`public/app.html`, `toggleSelectAll`/`bulkDeleteTransactions` משותפים לשלושתן) - לא נוסף נתיב API חדש; המחיקה המרובה פשוט קוראת ל-`DELETE` הקיים (`/api/transactions/:id` וכו') פעם אחת לכל תנועה מסומנת, במקביל (`Promise.all`), ומדווחת אם חלק נכשלו. תיבת "בחר הכל" מתעדכנת אוטומטית ל"לא מסומן" ברגע שמבטלים סימון של שורה בודדת.

### קטגוריית "הלוואות" - גם בתנועות הרגילות וגם בחתונה

משוב אמיתי: "אין קטגוריות בתנועות של הלוואות, גם בחתונה צריך שיהיה". נוספה "הלוואות" גם כהצעת קטגוריית הכנסה (לקיחת הלוואה) וגם הוצאה (החזר הלוואה) - ברשימת ההצעות הסטטית בתנועות הרגילות (`public/app.html`) וברשימת הקטגוריות הקבועות של "חתונה" (`WEDDING_INCOME_CATEGORIES`/`WEDDING_EXPENSE_CATEGORIES`).

### תוקן: תיאור תנועה מיובאת נעלם מהתצוגה (הוצג רק "אחר")

משוב אמיתי: "אני הטענתי אקסל, בהתחלה היה כתוב מסודר כל הכנסה מאיפה... אחרי יבוא השורות כתוב 'אחר' במקום שם, לדוגמא 200 בני מלך". התיאור המקורי מהקובץ (למשל "ניוד-בני מלך") נשמר נכון ב-DB (עמודת `note`) - הבעיה הייתה רק בתצוגה: רשימת "כל התנועות" ו"תנועות אחרונות" בסקירה הכללית הציגו רק את הקטגוריה (`t.category`, שברירת המחדל שלה היא "אחר" אם לא מולאה בתצוגה המקדימה) ומעולם לא הציגו את `t.note` - בניגוד ל"חתונה"/"דירה" ששם ה"הערה" כן מוצגת. נוסף `t.note` לשורת התת-כותרת בשתי הרשימות (`tx-list`, `ov-recent`), באותו פורמט בדיוק כמו בחתונה/דירה.

### תאריך היום בראש המסך

משוב אמיתי: "כל חודש כשאני מגיע לפנקס שיהיה תאריך מכוון כך אני יודע באיזה חודש אנחנו נמצאים". תאריך היום (יום+חודש+שנה בעברית, `toLocaleDateString('he-IL', ...)`) מוצג עכשיו קבוע בראש המסך (`#topbar-date`), בכל עמוד - לא רק בדוח החודשי הקיים שממילא מציג רק חודשים עם תנועות.

## גרפים בעמוד "תנועות" - הכנסות מול הוצאות, ופילוח קטגוריות

בקשת פיצ'ר ממשתמש: "בתנועות שיהיה גרף הכנסות מול הוצאות, או שיהיה עיגול עם צבעים" - שני הגרפים נוספו (לא רק אחד), כי הם מציגים שני דברים שונים ומשלימים:

- **גרף עמודות מקובצות** (`renderTrendChart` ב-`public/app.html`) - בכרטיס "דוח חודשי" הקיים, מעל הטבלה המדויקת (הטבלה נשארה - "טבלה + גרף" עדיף על גרף לבד: הגרף לקריאה מהירה, הטבלה לערכים מדויקים). עמודה ירוקה (הכנסות) ואדומה (הוצאות) לכל חודש, עם קווי רשת עגולים (0/1,000/2,000 וכו') וטולטיפ (hover) עם הסכום המדויק לכל עמודה.
- **גרף עיגול (donut)** (`renderCategoryDonut`) - כרטיס חדש "הוצאות לפי קטגוריה", עם סה"כ ההוצאות באמצע העיגול ומקרא (legend) לצידו עם צבע/סכום/אחוז לכל קטגוריה. מעל 6 קטגוריות מקפלים את השאר ל"אחר" (עיגול עם יותר מדי פרוסות נהיה קשה לקרוא).

**בלי שום ספריית גרפים חיצונית** (Chart.js וכו') - שני הגרפים הם SVG גולמי שנבנה ידנית ב-JavaScript (בדיוק כמו שאר הפרויקט, ר' "למה אפס תלויות" למעלה): עמודות כ-`<path>` עם פינות עליונות מעוגלות (בסיס ישר), עיגול כ-`<circle>` עם `stroke-dasharray`/`stroke-dashoffset` לכל פרוסה (הטריק הסטנדרטי לבניית donut בלי ספרייה).

**בחירת הצבעים**: לא הומצאו צבעים חדשים - נעשה שימוש בטוקנים שכבר קיימים באפליקציה (`--success` ירוק להכנסות, `--danger` אדום להוצאות - אותו צבע שכבר משמש את ה-pill/report-table הקיימים; `CATEGORY_COLORS` לקטגוריות - אותה רשימה שכבר שימשה את "הוצאות לפי קטגוריה" בסקירה הכללית). שני הצירופים (ירוק/אדום, וחמשת צבעי הקטגוריות) נבדקו מול `scripts/validate_palette.js` (מיומנות ה-dataviz) - עוברים את כל הבדיקות (הבחנה בעיוורון צבעים, ניגודיות וכו'), עם הסתייגות אחת: זוג ירוק/אדום נמצא ב"רצועת הסף" (ΔE 6.9 ל-deutan) שמחייבת קידוד משני מעבר לצבע בלבד - ולכן לכל עמודה יש גם מקרא טקסטואלי קבוע (לא רק צבע) וגם מיקום עקבי (הכנסה תמיד מימין להוצאה בכל קבוצה).

## הורים — סיכומים בלבד, לא הצ'אט הפנימי

נוסף מודל הרשאות ייעודי להורים:

- **תפקידים מקצועיים** (`mentor`/`therapist`) נקבעים בהרשמה או בעדכון פרופיל (`roles`) - הצהרה עצמית חופשית. **`supervisor` שונה**: הוא לא ניתן להצהרה עצמית בכלל, ודורש אישור "בעל הקו" - ר' סעיף ייעודי למטה. מי שיש לו אחד מהתפקידים המקצועיים (כולל `supervisor`), או שהוא הבעלים של התלמיד, מקבל גישה ל-`/file` המלא ולצ'אט הפנימי (`/comments`).
- **שיוך הורה לתלמיד** נעשה מבנית דרך טבלת `student_guardians` (לא דרך "הצהרה" חופשית על תפקיד) — כל איש צוות מקצועי (בעלים/חונך/מטפל/מפקח - לא רק הבעלים המקורי של התלמיד) יכול לשייך הורה, דרך `POST /api/students/:id/guardians` עם שם המשתמש של ההורה (שצריך להיות רשום מראש במערכת). הורה עצמו (חשבון בלי תפקיד מקצועי) לא יכול לשייך אף אחד, כולל את עצמו.
- ההורה רואה רק את `GET /api/students/:id/summary`: מספר מפגשים, סה"כ דקות, ורשימת הדוחות המקצועיים המלאים (זה בדיוק ה"סיכום" שההורה צריך). **אין** גישה לצ'אט הפנימי בין הצוות המקצועי, וגם **אין** גישה להערות (`student_comments`) — נתיב ה-`/summary` פשוט לא כולל אותן בכלל בתשובה.
- **סוגי דיווח מוצעים** (`role_type`): ריפוי בעיסוק, טיפול רגשי, תרפיה במוסיקה, תרפיה באומנות, תרפיה בחיות, אחר. בדיוק כמו trend, גם `role_type` יכול להיות כל ניסוח חופשי אחר (כשבוחרים "אחר" ומקלידים, למשל "פיזיותרפיה") - הרשימה היא הצעה נוחה, לא רשימה סגורה.
- **שמירה ושליחה הן שתי פעולות נפרדות**: `POST /api/students/:id/reports` תמיד שומר את הדוח בתיק המאוחד. האם לשלוח מייל להורים *עכשיו* נשלט ע"י שדה `notify_guardians` (בוליאני) בבקשה:
  - אם `notify_guardians` נשלח במפורש (`true`/`false`) — זה מה שקובע, בלי קשר למגמה (כך אפשר גם לשמור בלי לשלוח דוח עם מגמת "משתפרת", וגם לשלוח ביודעין דוח עם מגמה "יציבה").
  - אם `notify_guardians` לא נשלח בכלל — ברירת המחדל היא ההתנהגות המקורית: שולח מייל אוטומטית רק כשהמגמה היא **"משתפרת"**.
  - כדי לשלוח מאוחר יותר עדכון על דוח שכבר נשמר בלי שליחה מיידית, יש את `POST /api/reports/:id/notify` (מותר לאיש המקצוע שכתב את הדוח, או לכל בעלים/איש מקצוע אחר על אותו תלמיד).
  - בלוח הבדיקה (`test-dashboard.html`) זה מופיע כתיבת בחירה ("לשלוח עדכון במייל להורים המשויכים מיד עם השמירה") ורשימת "הדוחות שלי" עם כפתור "שלח עדכון להורים עכשיו" לכל דוח.
  - השליחה בפועל (`src/services/email.js`) פועלת במצב MOCK כרגע - ר' `.env.example`.
- **מגמה (`trend`) בניסוח חופשי**: מעבר לשלוש האפשרויות הקבועות (משתפרת/יציבה/דורשת תשומת לב), אפשר לשלוח כל טקסט חופשי (בלוח הבדיקה: לבחור "אחר" ולהקליד). רק הערך המדויק "משתפרת" מפעיל את ברירת המחדל של שליחת מייל אוטומטית - ניסוח חופשי דורש `notify_guardians: true` מפורש כדי לשלוח.
- **"מילון" ניסוחים אישי לכל איש מקצוע** (`phrase_dictionary`, `GET /api/reports/dictionary?kind=note|trend|role_type`): כל תוכן דיווח, וכל ניסוח מגמה/סוג-דיווח חופשי (לא אחת מהקטגוריות הקבועות), נשמר אוטומטית ב"מילון" האישי של איש המקצוע שכתב אותו, ומוצע כהשלמה אוטומטית (autocomplete) בפעם הבאה - גם עבור תלמידים אחרים - כדי לא להקליד את אותם ניסוחים מחדש בכל פעם.

## אבטחה ופרטיות — מה כבר מיושם

- סיסמאות מאוחסנות מוצפנות (scrypt+salt), לעולם לא בטקסט גלוי.
- התחברות דרך טוקן JWT חתום, עם תפוגה.
- שחזור סיסמה **אך ורק** בשיחה קולית אוטומטית שמקריאה קוד, או במייל — לעולם לא SMS.
- פרטי כרטיס אשראי **לעולם לא** מגיעים לשרת שלנו — הסליקה מתבצעת בדף/iframe מאובטח של Cardcom עצמם (תואם PCI-DSS).
- זיהוי מתקשר לפי מספר טלפון (Caller ID) מול הטלפון הרשום במערכת בלבד.
- תפקיד "מפקח" (גישה לכל תלמיד במערכת, לא רק תלמידים שרשמתם) לא ניתן להצהרה עצמית - דורש אישור בעל הקו (ר' סעיף ייעודי למעלה).
- קוד PIN/סיסמה נאכף בפורמט אחיד של 4 ספרות בדיוק בכל המערכת (ר' "קוד PIN" למעלה) - בטלפון תמיד נקלט בהקשת מקלדת בלבד (לא בדיבור, ולא מוקרא בקול בחזרה), כדי שלא יישמע/יזוהה שגוי ע"י מי שנמצא לצד המתקשר.

## מדריך פריסה לייצור — לאן לשלם ומה להגדיר

השלב הזה הוא שלכם (החלק העסקי/עמותה כבר בטיפולכם) — כאן רק ההוראות הטכניות המדויקות.

### 1. Twilio — מספר טלפון + שיחות קוליות

1. הרשמו בכתובת twilio.com וממלאים פרטי חיוב (כרטיס אשראי).
2. רוכשים מספר טלפון (מומלץ למצוא מספר ישראלי אם זמין, או מספר בינלאומי עם הפניה).
3. מהלוח הראשי (Console) מעתיקים את **Account SID** ואת **Auth Token**.
4. בהגדרות המספר שנרכש, תחת "Voice & Fax" → "A call comes in", בוחרים **Webhook**, ומדביקים: `https://הכתובת-שלכם.com/api/ivr/voice` (שיטה: HTTP POST).
5. ב-`.env` של השרת (העתיקו מ-`.env.example`) ממלאים:
   ```
   TWILIO_MOCK=false
   TWILIO_ACCOUNT_SID=...
   TWILIO_AUTH_TOKEN=...
   TWILIO_FROM_NUMBER=+972...   (המספר שרכשתם)
   PUBLIC_BASE_URL=https://הכתובת-שלכם.com
   RECOVERY_MOCK=false
   ```

חשוב: המשתמשים חייבים להיות רשומים במערכת עם מספר הטלפון שלהם בפורמט בינלאומי מלא (למשל `+972501234567`), אחרת זיהוי המתקשר לא יעבוד.

### 2. אחסון (Hosting) — היכן השרת רץ בפועל

השרת צריך שרת שרץ 24/7 עם כתובת ציבורית וכתובת HTTPS (חובה עבור Twilio), ועם **דיסק קבוע (persistent disk)** לשמירת קובץ מסד הנתונים (`data/app.db`) — אחרת המידע יימחק בכל עדכון.

אפשרויות פשוטות (לא דורשות ידע DevOps מעמיק):
- **Render.com** — "Web Service" מחובר ל-Git שלכם, עם "Persistent Disk" מחובר לתיקיית `data/`. פקודת הרצה: `npm start`.
- **Railway.app** — דומה, גם עם דיסק קבוע (Volume).
- שרת וירטואלי (VPS) כמו DigitalOcean/Linode — יותר שליטה, דורש קצת יותר הגדרה ידנית (Node.js + PM2 להרצה קבועה).

בכל אחת מהאפשרויות: מגדירים את משתני הסביבה מתוך `.env.example` בפאנל הניהול של השירות (לא מעלים את קובץ ה-`.env` עצמו ל-Git).

### 3. דומיין (אופציונלי אך מומלץ)

רוכשים דומיין (למשל דרך Namecheap/GoDaddy/ספק ישראלי), ומצביעים אותו לכתובת שקיבלתם משירות האחסון (לרוב באמצעות רשומת CNAME). מעדכנים את `PUBLIC_BASE_URL` ואת ה-Webhook ב-Twilio לכתובת הסופית.

### 4. Cardcom — הפעלת הסליקה האמיתית

מכיוון שכבר יש לכם Cardcom דרך העמותה:

1. נכנסים לפאנל הניהול של Cardcom ומאתרים את **מספר הטרמינל**, **שם ה-API** וה**סיסמה** (בדרך כלל תחת הגדרות/מסופים/API — אם לא מוצאים, פונים לתמיכת Cardcom ומבקשים "פרטי חיבור API ל-LowProfile").
2. ממלאים ב-`.env`:
   ```
   CARDCOM_MOCK=false
   CARDCOM_TERMINAL_NUMBER=...
   CARDCOM_API_NAME=...
   CARDCOM_API_PASSWORD=...
   ```
3. **חשוב לדעת**: הקובץ `src/services/cardcom.js` מכיל כרגע רק שלד (stub) לקריאה האמיתית ל-API של Cardcom, מכיוון שבנייתו הסופית דורשת פרטי טרמינל אמיתיים לבדיקה מולם (שאין לי גישה אליהם). לפני מעבר לתשלומים אמיתיים יש להשלים את הקריאה בפועל לפי התיעוד הרשמי של Cardcom (`docs.cardcom.solutions`), ולבדוק מול סביבת הבדיקות (Sandbox) שלהם. אשמח להשלים את זה יחד ברגע שיהיו לכם פרטי הטרמינל מול Cardcom.
4. שימו לב: הוראת קבע חודשית אצל Cardcom בדרך כלל מחייבת אוטומטית כל חודש מצידם לאחר ההגדרה הראשונית — כדאי לוודא מולם איך מגיע אישור/כישלון חיוב חוזר (Webhook מהם), כדי לעדכן את הסטטוס (`status`) בטבלת `subscriptions` בהתאם (שדה קיים במסד, אך חיבור ה-Webhook הזה טרם נבנה).

### 5. אבטחה לפני עלייה לאוויר

- ב-`.env` הגדירו `JWT_SECRET` לערך אקראי וארוך (למשל תוצאה של `openssl rand -hex 32`) — לא את ברירת המחדל.
- ודאו שכתובת השרת רצה על HTTPS (רוב שירותי האחסון הנ"ל נותנים את זה אוטומטית).
- כדי להפוך משתמש למנהל מערכת (לצורך שינוי תמחור התוכניות), יש להריץ פעם אחת ידנית מול מסד הנתונים:
  ```bash
  node -e "require('./src/db.js').prepare(\"UPDATE users SET roles = roles || ',admin' WHERE username = 'שם_המשתמש_שלכם'\").run()"
  ```

## מגבלות ידועות והמלצות להמשך

- **חיבור Cardcom האמיתי טרם הושלם** (ר' סעיף 4 למעלה) — נדרשים פרטי טרמינל אמיתיים להשלמה ובדיקה.
- **ספק מייל אמיתי טרם נבחר** — עדכוני ההורים במייל (ר' סעיף "הורים" למעלה) פועלים כרגע במצב MOCK בלבד (`src/services/email.js`) ומודפסים ללוג במקום להישלח באמת. יש לבחור ספק (SendGrid/Postmark/SES/SMTP) ולמלא פרטי API לפני מעבר לייצור.
- הרשאות "תפקיד מקצועי" (mentor/therapist/supervisor) הן כרגע "הצהרה עצמית" חופשית שכל משתמש קובע לעצמו בהרשמה/בפרופיל — אין עדיין אימות שמישהו שמצהיר על עצמו כ"מטפל" באמת עובד עם העמותה. לשיוך הורה-ילד יש כבר הגנה (רק הבעלים משייך), אבל לתפקידי צוות עדיין לא. שווה לשקול בעתיד תהליך אישור ידני על ידי מנהל לפני שתפקיד מקצועי נכנס לתוקף, אם ההיקף יגדל.
- אין עדיין מסך ניהול (UI) לעדכון תמחור התוכניות — כרגע זה נעשה דרך קריאת API ישירה (`PUT /api/plans/:id`) על ידי משתמש עם תפקיד `admin`. אפשר להוסיף למסך "הגדרות אישיות" באב-הטיפוס בעתיד אם רוצים.
- אין עדיין קליטת Webhook מ-Cardcom לעדכון סטטוס חיוב חוזר חודשי (הצלחה/כישלון) — מומלץ להוסיף בשלב חיבור ה-API האמיתי.
- **שקט/עיכוב מורגש בשלבי טקסט חופשי בימות כשזיהוי הדיבור המשודרג (Whisper) פעיל** (משוב אמיתי ממשתמש) — זה חל על שלבים ב-`FREE_TEXT_STATES` (למשל סכום הכנסה/הוצאה, שם), **לא** על שאלות האישור (אלה כבר עברו למצב הקשה טהור ללא עיכוב, ר' "תפריט הקטגוריות בטלפון" למעלה). הסיבה: כל שלב כזה כולל שתי קריאות רשת עוקבות - הורדת ההקלטה מימות ואז שליחתה ל-Whisper (ר' `speechToText.downloadAndTranscribe`) - לפני שאפשר להמשיך, בנוסף להמתנה הפנימית של ימות עצמה בשלוחת ההקלטה. זה תיעוד ידוע וקיים כבר בסעיף "זיהוי דיבור משודרג" למעלה ("זה משפר דיוק, לא מהירות") - לא תוקן כאן, כי זה trade-off מובנה בבחירה ב-Whisper, לא באג. אם העיכוב מפריע יותר מהתועלת בדיוק, אפשר לשקול לכבות את `WHISPER_RECORD_MODE_ENABLED` (`src/routes/yemot.js`) ולחזור למנוע הזיהוי הרגיל של ימות (מהיר יותר, פחות מדויק עם שמות).
